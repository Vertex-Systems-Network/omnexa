# P04.02 — Publish/Subscribe Abstraction & Ownership Boundaries

- Phase: `P04`
- State: `prepared / planned / locked`
- Owner/domain: `kernel.events`
- Depends on: `P04.01` accepted implementation **and** separate governed P04.01 closure/P04.02 activation transaction
- Blocks: `P04.03`
- Change class: `B`

> This document prepares the P04.02 contract only. It is **not implementation authority**. P04.02 source work must not begin until the separate closure/activation transaction merges and fresh protected `main` is re-read with P04.02 as the sole active package.

## Objective

Define the provider-neutral publish/subscribe boundary through which later Omnexa modules can publish validated P04.01 envelopes and register bounded consumers without selecting a broker, implementing durability, or creating cross-module write authority.

P04.02 establishes interface and ownership semantics only. It deliberately leaves durable streams/checkpoints, outbox/inbox, retry/DLQ, schema registry and business handlers to later packages.

## Required semantic boundary

The implementation must define a small kernel-owned abstraction that can prove:

- publishing accepts only a valid canonical P04.01 `Envelope`;
- subscription/handler registration is explicit, deterministic and bounded;
- each subscription declares the event contract(s) it consumes and the owning module/component identity;
- duplicate or conflicting registrations fail deterministically rather than silently overriding another owner;
- transport/publish acceptance never means business mutation success;
- duplicate delivery is possible and must remain visible in the contract assumptions;
- no global ordering guarantee is created;
- correlation/causation/tenant/classification metadata from P04.01 is preserved unchanged across the abstraction boundary;
- consumers cannot gain authority from the event envelope or transport layer;
- later adapters can implement the same contract without leaking vendor-specific types into domain modules.

## Ownership model

### Event producer ownership

- the producing module/domain owns the semantic event type and the fact that an authorized state transition emits it;
- `kernel.events` owns envelope validation and the transport-neutral publish/subscribe interfaces;
- P04.02 does not authorize a publisher to mutate another module's private state;
- publishing an event cannot bypass the producer's existing domain authorization/audit rules.

### Consumer ownership

- a consumer registration has one explicit owning module/component identity;
- handlers may invoke only already-authorized public capabilities/contracts for protected mutations;
- receipt of an event is not an authorization credential;
- tenant/org context must be validated before a tenant-scoped handler may perform protected work;
- a consumer must not write another module's private tables directly.

### Transport ownership

- P04.02 owns no concrete broker/provider;
- a later adapter may satisfy the abstraction only through a separately accepted package/change;
- domain packages must not import Kafka/NATS/RabbitMQ/Redis Streams/provider SDK types from this contract.

## Proposed contract responsibilities

Exact Go names may be refined during the governed implementation review, but the semantic roles must remain narrow:

### Publisher

A publisher accepts a validated canonical envelope plus cancellation/context and returns a deterministic result/failure representing only whether the abstraction accepted the publish operation.

It must not claim:

- durable persistence;
- downstream delivery;
- consumer execution;
- business mutation completion;
- exactly-once behavior.

### Subscription registry

The registry records bounded consumer registrations for explicit event contract identities.

A registration must include at minimum:

- stable owner/module identity;
- one or more explicit versioned event types or another equally bounded accepted selector;
- stable consumer/handler identity;
- handler reference compatible with repository conventions;
- no embedded credentials/provider configuration.

The registry must reject malformed, duplicate or conflicting identities deterministically.

### Handler invocation contract

The handler boundary receives the already-validated canonical envelope and execution context. It must preserve the original event identity/correlation/causation metadata and must not synthesize tenant authority from untrusted caller input.

P04.02 does not implement a worker loop, checkpoint, retry scheduler or durable consumer.

## Failure model

Failures must use existing stable safe failure conventions and distinguish at least conceptually:

- invalid/unacceptable envelope;
- invalid registration;
- duplicate/conflicting registration;
- unknown/unregistered route where applicable;
- handler/publish abstraction failure without leaking internal topology/secrets.

Do not expose provider connection strings, credentials, raw restricted payloads or stack traces through contract errors.

## Tenant / authorization / security invariants

- P04.01 envelope validation remains mandatory; P04.02 must not create a weaker parallel envelope parser;
- tenant-scoped consumption validates trusted tenant context fail-closed before protected mutation;
- event metadata never grants permission/capability/role authority;
- cross-tenant routing or handler context mismatch fails closed;
- restricted/confidential payloads are not logged by the abstraction;
- publisher/consumer identities are bounded and validated;
- secret/provider configuration is structurally outside the event contract;
- cancellation/context propagation must not be silently discarded where the repository's Go conventions require it;
- malformed input must not panic or register partial hidden state.

## Duplicate and ordering assumptions

P04.02 must preserve these accepted P04 laws:

- duplicate publish/delivery can occur;
- retries/replays may later re-deliver the same event;
- no global ordering guarantee exists;
- transport acceptance does not imply mutation success;
- later protected consumers must be application-idempotent;
- provider claims of exactly-once delivery cannot replace application duplicate-safety evidence.

P04.02 may expose these assumptions through documentation/types/tests but must not implement the durable idempotency mechanism owned by later packages.

## Negative requirements

P04.02 MUST NOT:

- add Kafka, NATS, RabbitMQ, Redis Streams or another broker dependency;
- add provider/vendor SDK configuration;
- add database migrations;
- implement durable stream storage or consumer checkpoints (`P04.03`);
- implement transactional outbox (`P04.04`);
- implement consumer inbox/deduplication persistence (`P04.05`);
- implement retry/backoff or DLQ/quarantine (`P04.06`);
- implement schema registry/evolution runtime (`P04.07`);
- change background-job ownership/execution (`P04.08`);
- add business-domain event handlers;
- modify business-feature authorization;
- add unrestricted generic RPC/service-mesh behavior;
- create a second event-envelope model competing with P04.01;
- introduce AI/model/agent authority.

## Expected implementation path budget

The later implementation should remain approximately within:

- `kernel/internal/events/bus.go` (or one equivalently named provider-neutral contract file);
- `kernel/internal/events/bus_test.go`;
- narrowly required existing `kernel/internal/events` exports/utilities only if proven necessary;
- `scripts/verify_p04_02.sh` if the repository's retained verifier convention is continued;
- package evidence/checkpoint artifacts required by governance.

Expansion into migrations, job runtime, module lifecycle, auth core, business modules or CI architecture triggers re-plan/change control.

## Required tests / acceptance criteria

Before P04.02 promotion, prove on the exact candidate head:

1. a valid P04.01 envelope can cross the publish abstraction without identity/correlation/tenant/classification mutation;
2. an invalid envelope fails before publish/handler acceptance;
3. deterministic valid registration succeeds;
4. malformed registration fails safely;
5. duplicate/conflicting registration cannot silently replace another consumer;
6. explicit owner/module identity is retained and cannot be omitted where required;
7. tenant/context mismatch fails closed at the boundary that P04.02 can prove without inventing later durable runtime;
8. publish acceptance is not represented as downstream/business completion;
9. duplicate/no-global-order assumptions remain explicit in tests/contracts;
10. errors/loggable metadata do not expose secrets or raw restricted payloads;
11. no broker/provider, migration, durable checkpoint, outbox/inbox, retry/DLQ, business handler or background-job change appears in the diff;
12. repository Go quality and every retained P01/P02/P03/P04.01 regression remain green under exact-head Omnexa Governance.

## Fast implementation gate

Use focused evidence first:

- `go test` for `kernel/internal/events`;
- formatter/vet/static checks on changed Go paths;
- focused registration/tenant/duplicate/adversarial tests;
- package verifier if created.

## Full package gate

Before promotion require canonical Omnexa Governance on the exact final head, including retained repository Go quality and all mandatory predecessor regressions. Source-carrier green evidence is not promotion authority; an unchanged promotion carrier must obtain its own fresh governance according to repository convention.

## Data / migration / rollback

- database migration: `none`;
- persisted business-data mutation: `none`;
- provider/spend: `none`;
- rollback class: `SIMPLE ROLLBACK` before later packages depend on the abstraction;
- after P04.03+ depends on the accepted interface, evolve compatibly through governed change rather than rewriting P04.02 historical evidence.

## Definition of Done

P04.02 is done only when:

- the separate P04.01 closure/P04.02 activation transaction has first made P04.02 the sole authorized package;
- implementation stays within the accepted provider-neutral boundary;
- positive and adversarial tests pass;
- exact-head canonical Governance passes;
- review classification is recorded honestly;
- promotion merges through the governed integration path;
- P04.02 completion evidence is recorded;
- a later separate transition decides whether P04.03 may activate.

`P04.03` and all business-feature/AI authority remain locked until that later transaction.
