# P04.03 — Durable Stream/Consumer Baseline & Checkpoint Model

- Phase: `P04`
- State: `prepared / planned / locked`
- Owner/domain: `kernel.events`
- Depends on: accepted `P04.01`, accepted P04.02 implementation/completion evidence, and a separate governed P04.02 closure/P04.03 activation transaction
- Blocks: `P04.04`, `P04.06`, `P04.09`
- Change class: `B`

> This document prepares the P04.03 contract only. It is **not implementation authority**. P04.03 runtime/source work must not begin until a separate governance/state/continuity transaction records P04.02 done, explicitly accepts this contract, makes P04.03 the sole active package, passes exact-head Omnexa Governance, merges through the protected path, and protected `main` is re-read.

## Objective

Define the provider-neutral durable stream/consumer and checkpoint boundary needed to resume event consumption safely after interruption without selecting a broker, implementing transactional outbox/inbox, claiming exactly-once delivery, or granting business-domain write authority.

P04.03 establishes the minimum durability and checkpoint semantics on top of the accepted P04.01 envelope and P04.02 publish/subscribe ownership contracts. It deliberately leaves transactional outbox, inbox/deduplication persistence, retry/DLQ, schema registry, background jobs, and business handlers to later packages.

## Required semantic boundary

A later authorized implementation must prove:

- durable consumption operates only on valid canonical P04.01 envelopes routed through accepted P04.02 ownership identities;
- a consumer position/checkpoint is scoped to an explicit stable consumer identity and stream/partition-equivalent scope, never a hidden global cursor;
- checkpoint advancement is monotonic within its declared scope and cannot silently move backwards or jump across an unprocessed event;
- restart/resume begins from the last accepted checkpoint according to one documented boundary convention;
- delivery may repeat around crash/restart boundaries; duplicate delivery remains an explicit application-level concern;
- checkpoint persistence does **not** mean protected business mutation was applied exactly once;
- no global event ordering guarantee is introduced;
- tenant, event identity, correlation, causation, schema version, and classification metadata remain unchanged and authoritative;
- a checkpoint or transport offset is never an authorization credential;
- provider-specific offsets/types/configuration do not leak into domain modules or the canonical event contract.

## Durable consumer identity

Each durable consumer must have a stable identity compatible with the P04.02 ownership model. At minimum the durability boundary must bind:

- owner/module identity;
- stable consumer identity;
- explicit event route/contract identity;
- explicit stream/shard/partition-equivalent scope where the implementation needs one;
- trusted tenant context when consumption is tenant-scoped.

Rebinding the same stable consumer identity to a conflicting owner or incompatible durable scope must fail deterministically rather than silently inheriting another consumer's checkpoint.

## Checkpoint model

The checkpoint contract must be intentionally narrow:

- checkpoint state represents **consumption progress only**;
- the checkpoint key/scope is explicit and stable;
- advancement occurs only after the consumer boundary has reached the accepted acknowledgement point defined by this package;
- a failed or cancelled handling attempt must not advance beyond work that has not reached that acknowledgement point;
- restart must not require guessing an implicit cursor;
- stale/conflicting checkpoint writes must fail closed or be rejected through deterministic optimistic/monotonic rules;
- checkpoint state must not contain raw restricted/confidential event payloads or secrets.

The exact storage mechanism remains provider-neutral in this contract. If durable storage requires a repository persistence adapter or migration, that must be separately proven to fit the P04.03 path/data budget before implementation; this prepared contract itself adds no migration and selects no provider.

## Crash/restart and acknowledgement law

P04.03 must preserve at-least-once-compatible semantics:

- a crash before accepted checkpoint advancement can cause the event to be delivered again;
- a crash after a downstream business mutation but before checkpoint advancement can also cause re-delivery;
- therefore application-level idempotency remains mandatory for protected consumers;
- no provider or storage feature may be described as proving end-to-end exactly-once business mutation;
- checkpoint advancement and business mutation are not silently treated as one transaction in P04.03; transactional reliability mechanisms belong to P04.04/P04.05 and later acceptance work.

## Ordering model

- no global ordering guarantee exists;
- ordering may only be reasoned about inside an explicit durable scope if the later implementation can prove it;
- checkpoint comparison/advancement must never infer ordering across unrelated streams, tenants, partitions, owners, or consumer identities;
- parallelism must not allow a later event to advance the checkpoint past an earlier unacknowledged event in the same ordered scope.

## Failure model

Use existing safe failure conventions and distinguish conceptually:

- invalid durable consumer identity/scope;
- missing or malformed checkpoint;
- stale/regressive/conflicting checkpoint update;
- durable-read/write failure without leaking provider topology or credentials;
- cancellation/interruption;
- P04.01 envelope validation failure;
- P04.02 ownership/registration mismatch.

Failures must not expose credentials, connection strings, provider topology, stack traces, raw restricted payloads, or cross-tenant metadata.

## Tenant / authorization / security invariants

- trusted tenant context remains fail-closed before tenant-scoped protected work;
- event metadata, durable offsets, checkpoint tokens, or consumer IDs never grant role/capability authority;
- cross-tenant checkpoint reuse or consumer-scope collision fails closed;
- durable state keys must be bounded/validated and must not permit caller-controlled cross-owner namespace escape;
- restricted/confidential payloads are not copied into checkpoint metadata or logs;
- cancellation/context propagation must be preserved according to repository Go conventions;
- malformed durable state must not panic, partially advance hidden state, or silently reset to a permissive default.

## Negative requirements

P04.03 MUST NOT:

- activate or implement P04.04+;
- select Kafka, NATS, RabbitMQ, Redis Streams or another broker/provider;
- claim exactly-once delivery or exactly-once business mutation;
- implement transactional outbox (`P04.04`);
- implement inbox/deduplication persistence (`P04.05`);
- implement retry/backoff or DLQ/quarantine (`P04.06`);
- implement schema-registry runtime (`P04.07`);
- change background-job ownership/execution (`P04.08`);
- add business-domain event handlers or cross-module private-table writes;
- weaken P04.01 envelope validation or P04.02 ownership constraints;
- turn a checkpoint/offset into an authorization capability;
- grant business-feature or AI/model/agent authority.

## Expected implementation path budget

The later implementation carrier must re-read the repository and record an exact path budget before source mutation. The expected bounded shape is:

- narrowly scoped `kernel/internal/events` durable-consumer/checkpoint contract and implementation files;
- focused `kernel/internal/events` tests for monotonicity, restart, cancellation, scope conflict, tenant mismatch and duplicate-delivery boundaries;
- a storage adapter only if the accepted activation transaction explicitly authorizes the required persistence path and any migration separately;
- package verifier/evidence artifacts required by governance.

Expansion into business modules, auth core, job runtime, provider SDKs, generic broker topology, outbox/inbox, retry/DLQ, or CI architecture triggers re-plan/change control.

## Required tests / acceptance criteria

Before P04.03 promotion, the later implementation must prove on its exact candidate head:

1. a valid durable consumer resumes from the last accepted checkpoint after simulated interruption;
2. a failed/cancelled unacknowledged event cannot advance the checkpoint past itself;
3. checkpoint advancement is monotonic within one explicit scope;
4. stale/regressive/conflicting advancement is rejected deterministically;
5. the same consumer identity cannot be rebound across conflicting owners/scopes;
6. unrelated consumers/tenants/scopes cannot read or advance each other's checkpoints;
7. duplicate delivery around crash/restart remains possible and explicitly tested/documented;
8. no global ordering or exactly-once claim appears in behavior or documentation;
9. P04.01 metadata and P04.02 ownership identity are preserved across durable consumption;
10. malformed durable/checkpoint state fails safely without panic or permissive reset;
11. errors/loggable metadata do not expose secrets or raw restricted payloads;
12. no P04.04+, provider-specific, business-handler, background-job, or AI/runtime authority change appears in the diff;
13. repository Go quality and all retained P01/P02/P03/P04.01/P04.02 regressions remain green under exact-head Omnexa Governance.

## Data / migration / rollback

- this preparation carrier: database migration `none`, persisted business-data mutation `none`, provider/spend `none`;
- later P04.03 implementation must not assume a migration is automatically authorized by this document;
- if persistence schema is required, the activation/implementation plan must name it explicitly, prove tenant/isolation/rollback behavior, and keep it inside P04.03 rather than smuggling P04.04/P04.05 semantics into the package;
- rollback must preserve already accepted P04.01/P04.02 contracts and must not rewrite historical completion evidence.

## Definition of Done

P04.03 is done only when:

- a separate P04.02 closure/P04.03 activation transaction first makes P04.03 the sole authorized package;
- implementation stays within the accepted durable-consumer/checkpoint boundary;
- crash/restart, monotonicity, duplicate, tenant/scope and failure tests pass;
- exact-head canonical Governance passes;
- review provenance is recorded honestly;
- promotion merges through the governed integration path;
- P04.03 completion evidence is recorded;
- a later separate transition decides whether P04.04 may activate.

`P04.04+`, business-feature code, and AI/model/agent runtime remain locked until their later governed transactions.
