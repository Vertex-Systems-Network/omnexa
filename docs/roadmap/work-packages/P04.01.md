# P04.01 — Event Envelope & Identity Contract

- Phase: `P04`
- State: `active`
- Owner/domain: `kernel.events`
- Depends on: P03 exit gate satisfied
- Blocks: `P04.02`
- Change class: `B`

> This specification is the sole active P04 implementation boundary after the governed P04 activation transaction. It authorizes only the contract-first P04.01 scope below; P04.02+ and business-feature code remain locked.

## Objective

Define the canonical, provider-neutral event envelope and deterministic validation contract used by later P04 transport, outbox/inbox, retry, schema-registry, job-correlation and replay packages.

P04.01 defines **data and validation semantics only**. It must not select a broker or implement asynchronous delivery.

## Actors / consumers

- kernel-owned publishers that have already completed an authorized domain state transition;
- kernel/module consumers receiving validated event metadata in later packages;
- audit/observability tooling that may read classification-safe event identity and correlation metadata;
- test/governance tooling validating deterministic event contracts.

AI/model/agent systems are not event-transport authorities and gain no new write capability from this package.

## Required envelope fields

The canonical v1 event envelope must define, validate and serialize at minimum:

- stable globally unique `event_id`;
- stable `event_type` / contract identity;
- explicit `event_version`;
- `producer` identity;
- explicit tenant/org context where the event is tenant-scoped;
- `occurred_at` UTC instant;
- optional later publication timestamp must not replace occurrence time;
- `correlation_id`;
- optional `causation_id` with self-causation rejection;
- classification / payload-sensitivity metadata compatible with existing data-classification law;
- bounded structured payload or payload reference contract;
- deterministic content/contract validation errors.

Identifiers must use existing Omnexa identifier standards rather than inventing an incompatible local scheme.

## Delivery assumptions established now

P04 must assume:

- duplicate publish/delivery can occur;
- no global ordering guarantee exists unless a later bounded package proves one;
- retries/replays may re-deliver the same event;
- transport success does not imply domain mutation success;
- an event never grants cross-domain write authority;
- consumers must remain idempotent where protected mutations are possible.

Claims of broker-level “exactly once” must never replace application-level duplicate-safety evidence.

## Tenant / authorization / security invariants

- tenant context is explicit and validated fail-closed;
- cross-tenant event context mismatch is rejected before later handler execution;
- publisher identity does not bypass domain authorization;
- event transport cannot mutate another module's private tables directly;
- no passwords, tokens, private keys, credentials or unrestricted secret values in event payloads/metadata;
- restricted/confidential fields follow existing classification/minimization rules;
- payload size/depth/string/collection bounds are explicit and tested;
- malformed/untrusted event input cannot panic, execute code or expose internal topology;
- diagnostic errors remain stable and safe.

## Versioning / compatibility

P04.01 must establish an explicit envelope version. Unknown future envelope versions fail closed unless a later accepted compatibility policy authorizes them.

Event-type payload schema evolution is owned by later `P04.07`; P04.01 must leave a stable version hook without prematurely implementing a schema registry.

## Negative requirements

P04.01 MUST NOT:

- add Kafka, NATS, RabbitMQ, Redis Streams or another broker dependency;
- add database migrations;
- implement outbox/inbox persistence;
- implement durable consumers, checkpoints, retry queues or DLQ/quarantine;
- add business-domain handlers;
- add background-job execution changes;
- change business-feature authorization;
- expose unrestricted raw payloads in logs;
- infer tenant authority from a caller-supplied string without validation;
- treat transport acceptance as business acceptance.

## Expected implementation path budget

The later P04.01 implementation carrier is expected to stay within approximately:

- `kernel/internal/events/envelope.go`
- `kernel/internal/events/envelope_test.go`
- optional narrowly-required existing shared identifier/time/error utility imports only; no unrelated shared refactor;
- `scripts/verify_p04_01.sh` if the repository's package-verifier convention is retained;
- generated/spec evidence and package checkpoint files required by governance.

Unexpected expansion into manifests, module lifecycle, auth core, migrations, CI architecture or business modules triggers re-plan/change control before continuing.

## Acceptance criteria

1. valid envelope v1 round-trips deterministically;
2. event ID/type/version/producer/correlation/tenant/time fields validate against explicit bounded rules;
3. missing or malformed required identity fails with stable safe errors;
4. self-causation and invalid correlation/causation identities fail closed;
5. tenant-scoped event without valid tenant context fails closed;
6. cross-tenant context mismatch test exists at the contract boundary that can be proven in P04.01 without inventing later handler runtime;
7. secret-looking prohibited metadata/payload fields are rejected or structurally impossible according to the accepted payload contract;
8. oversized/deep malformed inputs are bounded;
9. no broker, migration, outbox/inbox, retry/DLQ or business handler appears in the P04.01 diff;
10. repository Go quality and all retained P01/P02/P03 regressions remain green on exact GitHub-hosted head.

## Fast gate during implementation

Use focused checks first:

- `go test` for the event-envelope package;
- formatter/vet/static checks on changed Go paths;
- package verifier if created.

## Full package gate

Before P04.01 promotion require canonical Omnexa Governance on the exact candidate head, including retained repository Go quality and all mandatory prior-phase regressions.

## Data / migration / rollback

- database migration: none;
- persisted data mutation: none;
- external provider/spend: none;
- rollback class: `SIMPLE ROLLBACK` before later packages depend on the contract;
- once later P04 packages depend on envelope v1, evolve compatibly through an accepted versioning change rather than rewriting historical contract evidence.

## Definition of Done

P04.01 is not done until implementation, negative tests, exact-head governance, review classification, package evidence, state/checkpoint update and next-package lock/activation transaction are complete.

`P04.02` must remain locked until a separate governed completion transition accepts P04.01.
