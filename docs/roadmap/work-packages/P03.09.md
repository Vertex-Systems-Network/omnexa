# P03.09 — Migration Ownership Registry

- Phase: `P03`
- State: `planned`
- Owner/domain: `kernel.modules` integrated with the P01 database/migration foundation
- Depends on: `P03.08`
- Blocks: `P03.10`
- Change class: `B`

> Readiness only. `business_feature_code_authorized=false`; module migration execution must preserve existing database authority and owner boundaries.

## Objective

Bind ordered/versioned migrations to module ID/version/authoritative owner so fresh install and supported upgrade paths can be proven without allowing cross-module schema mutation or environment-specific manual database changes.

## In scope

- migration identity/order/module/version/owner registry metadata;
- ownership checks against module/domain boundaries;
- fresh-install and supported-upgrade planning/validation;
- destructive/backfill classification metadata and lifecycle coordination;
- duplicate/order/conflict detection;
- representative migration fixtures used by P03 exit proof.

## Out of scope

- replacing the P01 migration engine;
- cross-domain schema ownership changes without ADR;
- marketplace arbitrary SQL execution;
- P04 event/outbox migrations beyond their later phase.

## Security and architecture invariants

- a module may migrate only owned schema unless an explicitly approved platform migration says otherwise;
- direct cross-module table mutation is forbidden;
- migration inputs/paths are not arbitrary user-controlled file execution;
- destructive operations require explicit documented strategy and lifecycle authorization;
- migrations preserve tenant boundaries and data integrity;
- retries/concurrency cannot double-apply a migration.

## Acceptance criteria

1. migration metadata binds deterministic order to module/version/owner and rejects duplicate/conflicting identities.
2. cross-owner schema mutation fixtures are rejected unless explicitly approved by canonical governance.
3. fresh install and representative supported upgrade paths are mechanically testable without manual SQL.
4. destructive/backfill requirements are explicit and cannot be hidden as ordinary compatible migration.
5. lifecycle upgrade/failure behavior preserves a recoverable/forward-fix state.
6. tenant isolation and existing P01 migration regressions remain intact.
7. Go quality and all P01/P02 regressions pass on GitHub-hosted `ubuntu-24.04`.

## Completion evidence

None while planned; future exact-head P03.09 verifier and migration evidence required.

## State transition

`planned -> active -> verification -> done`; P03.10 remains planned until separate transition.
