## Objective

Define the minimum provider-neutral failure-disposition, bounded retry/backoff, terminal-failure, and logical dead-letter/quarantine contract for durable P04 event consumption.

P04.06 must compose the accepted P04.03 checkpoint and P04.05 inbox/idempotency primitives without merging their meanings:

- a retryable handler failure must not advance durable progress;
- a duplicate/already-applied P04.05 outcome is not a failure and may recover checkpoint progress through the accepted handler-success path;
- a terminal or retry-exhausted event must be durably quarantined **before** durable progress may move past it;
- a crash after quarantine commit but before checkpoint advancement must be restart-safe: redelivery recognizes the accepted quarantine state, does not invoke the handler again, and may recover the checkpoint;
- no retry/quarantine record is an authorization credential, successful business outcome, inbox completion, or exactly-once proof.

This package closes the durable-consumer retry/poison-event scheduling and terminal-state boundary only. It does not define event schema compatibility (`P04.07`), background-job ownership/execution changes (`P04.08`), broad reliability/operator recovery UX (`P04.09`), or controlled replay/release/poison-event aggregate acceptance (`P04.10`).

## Failure disposition law

P04.06 requires an explicit deterministic disposition for a failed delivery. Minimum dispositions are:

- `retryable` — a later attempt is allowed by both structured failure evidence and the event/operation idempotency policy;
- `terminal` — the current event cannot be automatically retried and must move to durable quarantine before progress can move past it;
- `interrupted` — caller/system cancellation or shutdown prevented an authoritative attempt outcome; it does not consume retry budget and does not advance progress;
- `success` / `already_applied` — not failures; these remain the accepted success/duplicate-safe path and are not written as terminal retry evidence.

Classification requirements:

1. classification must use stable machine evidence, never string matching against raw error text;
2. a canonical P01.03 failure marked `Retryable=true` is only **eligible input** to retry classification; the flag does not by itself prove that repeating the protected action is safe;
3. automatic retry is allowed only when the relevant handler operation is covered by accepted idempotency/duplicate-safety semantics, including P04.05 where local protected mutation is involved;
4. a canonical failure marked non-retryable must not be silently upgraded to retryable by a generic category mapping;
5. unstructured/unknown errors default fail-closed to terminal unless an accepted owner classifier converts them into a stable structured retryable failure before they reach the P04.06 boundary;
6. validation, authorization, authentication, invariant, conflict, or not-found categories must not be globally auto-retried merely because a later environment change is conceivable;
7. dependency/rate-limit/timeout/unavailable categories may be retry candidates only when `Retryable=true` and the operation-safety gate passes;
8. `context.Canceled`, controlled shutdown, and equivalent non-authoritative interruption are not terminal business failures and do not consume retry attempts;
9. deadline outcomes are classified using the stable structured failure contract rather than raw context text; cancellation caused by process shutdown must remain distinguishable from a retryable dependency timeout where possible;
10. classification must be deterministic for the same stable failure evidence and policy version.

A later implementation may expose a narrow provider-neutral `FailureClassifier`/`Disposition` seam. It must not give arbitrary transport adapters authority to redefine domain failure semantics.

## Bounded retry policy law

Automatic retry must always be finite and deterministic.

The V1 logical policy must include at least:

- stable policy ID/version;
- `max_attempts` including the first handler attempt;
- `initial_backoff`;
- `max_backoff`;
- deterministic capped exponential backoff;
- optional bounded policy metadata required to explain the accepted decision.

Required algorithmic law for an accepted policy:

- attempt numbers start at `1`;
- after a retryable failure on attempt `n`, another automatic attempt is eligible only if `n < max_attempts`;
- delay is `min(initial_backoff * 2^(n-1), max_backoff)` with overflow-safe saturation;
- `next_eligible_at = authoritative_failure_time + delay`, normalized to UTC;
- no V1 random/unbounded jitter is required; if later introduced it must be deterministic/bounded enough for reproducible evidence and cannot schedule before the base backoff floor;
- when `n >= max_attempts`, the event becomes terminal by exhaustion and must enter quarantine;
- `max_attempts`, delay values, due-scan batch sizes, and claim/lease duration must have explicit hard upper bounds in code before runtime acceptance;
- zero/negative durations, unbounded integers, caller-selected arbitrary retry counts, and immediate infinite loops are invalid;
- retry policy is snapshotted/versioned for an in-flight processing identity so configuration changes do not silently rewrite historical attempt accounting.

This preparation does not freeze exact numeric V1 constants. Activation/implementation preflight must set them from fresh protected main and prove they are finite, operationally sane, and no broader than required. P01.09's existing job constants are informative precedent only and are not automatic P04.06 authority.

## Processing identity and attempt law

Retry state must bind to the same accepted durable processing scope used by P04.03/P04.05, including at least:

- canonical EventID;
- owner/module scope;
- stable consumer identity;
- event type/route identity;
- stream/partition scope;
- trusted tenant scope where applicable.

Requirements:

- EventID alone is not a global retry/quarantine lock across consumers;
- one consumer/tenant/route cannot inspect, claim, retry, quarantine, or resolve another scope's state;
- an attempt number is monotonic for one exact processing identity and policy snapshot;
- concurrent workers cannot both claim the same eligible retry attempt as distinct authoritative attempts;
- losing/duplicate claims resolve deterministically without double-incrementing attempt count;
- an already-completed P04.05 inbox identity must suppress protected mutation even if stale retry evidence exists;
- route/owner/tenant/consumer rebinding fails before handler invocation;
- conflicting canonical content/fingerprint remains a P04.05 conflict, not a retry opportunity.

## Durable retry state machine

The minimum provider-neutral durable states are logically equivalent to:

- `retry_scheduled` — prior authoritative failure was retryable, budget remains, and a later eligibility time exists;
- `quarantined` — failure is terminal or retry budget exhausted; automatic handler invocation is forbidden;
- `resolved` — the processing identity later completed/already-applied and any stale scheduled retry must no longer invoke the handler.

Exact names/storage representation are implementation details, but transitions must obey:

1. first delivery has no requirement for a pre-created retry row;
2. authoritative retryable failure durably records/increments the attempt evidence and next eligibility before returning a scheduled/deferred outcome;
3. delivery before `next_eligible_at` does not invoke the handler, does not increment attempts, does not advance checkpoint, and returns a deterministic deferred outcome;
4. an eligible retry must first obtain an authoritative one-at-a-time claim/lease/CAS for that processing identity;
5. successful handler completion or P04.05 already-applied outcome resolves stale retry scheduling before it can trigger another automatic handler invocation;
6. non-retryable failure or exhausted attempt budget durably transitions to `quarantined`;
7. quarantined state is immutable to ordinary automatic delivery processing; only a later separately authorized P04.09/P04.10 operator/replay contract may release/replay it;
8. persistence failure while scheduling/quarantining cannot be treated as success and cannot advance checkpoint;
9. cancellation before an authoritative failure result does not create a false attempt increment or quarantine record;
10. corrupted/unknown state fails closed.

A retry coordinator must not sleep/block a worker until due time as the canonical scheduling mechanism. It returns bounded eligibility state; a later provider/worker adapter may poll/claim due records under this contract without becoming the policy authority.

## Checkpoint, inbox and quarantine interaction law

P04.03 checkpoint, P04.05 inbox, and P04.06 retry/quarantine records are three distinct facts:

- checkpoint = durable ordered consumption progress;
- inbox completion = duplicate-safe local protected mutation evidence;
- retry/quarantine = failure disposition, automatic-attempt budget, next eligibility, and terminal poison-event evidence.

### Retryable failure

- handler failure classified retryable does **not** advance checkpoint;
- retry scheduling state must be durable before the delivery is represented as intentionally deferred;
- redelivery before eligibility skips handler and checkpoint advancement;
- redelivery after eligibility may claim the next attempt;
- if a prior protected mutation actually committed and P04.05 recorded completion but checkpoint did not advance, redelivery resolves through `already_applied` and must not be converted into another failed/retry attempt.

### Terminal/quarantined failure

To prevent one poison event from permanently blocking an ordered scope without erasing its failure:

1. terminal/exhausted disposition must first commit durable quarantine evidence for the exact processing identity and delivery position;
2. only after authoritative quarantine exists may the durable consumer acknowledge/advance the P04.03 checkpoint past that exact quarantined position;
3. quarantine persistence failure means checkpoint must not advance;
4. crash after quarantine commit but before checkpoint advancement is safe: redelivery discovers the exact quarantine state, does not invoke the handler, and may retry checkpoint advancement;
5. checkpoint advancement failure after quarantine must not erase or downgrade quarantine evidence;
6. checkpoint state must not itself be used to claim that quarantine/retry evidence exists;
7. quarantine must not create a fake P04.05 inbox completion or business-success result.

The later implementation must make the exact terminal-acknowledgement API explicit and test the crash gap on real persistence. It may compose stores sequentially only where failure ordering preserves the laws above; it must not pretend separate transactions are atomic if they are not.

## Retry claim / concurrency law

A later implementation must prove one authoritative eligible attempt at a time per processing identity.

Minimum requirements:

- durable CAS/row-lock/lease claim uses server/authoritative time, not caller-provided timestamps;
- claim has a bounded lease/expiry so process death cannot strand the identity forever;
- claim expiry does not itself increment attempt count;
- the attempt is counted only when an authoritative handler attempt begins/has a classified outcome according to the accepted implementation convention;
- two concurrent claimers cannot both create separate next-attempt transitions for one prior attempt;
- stale claim completion cannot overwrite a newer attempt/quarantine/resolved state;
- tenant/owner/consumer scopes remain isolated under concurrency;
- database deadlock/serialization/unavailable failures do not create false success/quarantine and do not busy-loop internally.

P04.05 remains the final local protected-mutation duplicate-safety boundary; P04.06 concurrency control does not replace inbox idempotency.

## Quarantine / dead-letter law

For V1, `dead-letter` is a **logical local quarantine state/record**, not authority to provision or depend on a broker-specific DLQ.

A quarantine record should contain only bounded safe evidence needed for diagnostics/recovery, such as:

- exact processing identity components or their bounded canonical representation;
- delivery position and canonical EventID;
- policy ID/version and attempts consumed;
- terminal reason (`non_retryable`, `attempts_exhausted`, or another finite accepted code);
- stable safe P01.03 failure code/category and retryability bit where present;
- first/last failure timestamps and quarantine timestamp;
- bounded correlation identifiers already allowed by P01.03/P01.07;
- canonical fingerprint/reference required to detect conflicting reuse, without duplicating restricted event payload.

It MUST NOT store by default:

- raw handler/provider/database error text;
- stack traces;
- SQL/provider payloads;
- secrets/tokens/credentials;
- unrestricted event payload copies;
- business-domain private state;
- authorization decisions as reusable credentials.

P04.06 may define bounded read/inspect semantics needed for tests/diagnostics, but broad operator actions, release/requeue/replay UI/API, bulk poison-event operations, or destructive purge remain P04.09/P04.10 unless separately authorized.

## Payload, privacy and observability law

- confidential/restricted payload must not be copied into retry logs or quarantine metadata merely for convenience;
- event payload remains owned by the accepted event/outbox source of truth; P04.06 stores failure/scheduling evidence, not a second event archive;
- safe structured logs/metrics may report counts, bounded machine codes, attempt numbers, delay buckets and correlation IDs under P01.07 rules;
- high-cardinality raw EventID/tenant/user identifiers must not be blindly promoted to metric labels;
- retry/quarantine persistence is not a substitute for P01.11 audit transport;
- privileged later operator release/replay actions require their own audit/authorization evidence;
- failure detail projected publicly must stay within the P01.03 safe structured failure contract.

Before later P04.06 promotion, the authorized implementation must prove on its exact final head at least:

1. stable structured retryable failure schedules one bounded next attempt without advancing checkpoint;
2. non-retryable structured failure enters quarantine without an automatic retry;
3. unknown/unstructured failure fails closed according to the accepted terminal-default law;
4. interruption/cancellation does not consume attempt budget, create quarantine, or advance checkpoint;
5. attempt numbers are monotonic and never exceed the configured finite maximum;
6. capped exponential delay/UTC next-eligibility is deterministic, overflow-safe, and never earlier than policy allows;
7. delivery before eligibility does not invoke the handler or increment attempts;
8. eligible delivery obtains only one authoritative claim under concurrency;
9. process death/claim expiry permits later recovery without double-counting an attempt;
10. two concurrent claimers cannot both become authoritative for the same attempt;
11. success after prior retryable failures resolves stale scheduling and advances checkpoint through the retained P04.03 path;
12. P04.05 already-applied redelivery resolves as success/duplicate-safe and never reruns the protected mutation;
13. retryable failure followed by storage failure cannot be falsely represented as durably scheduled or acknowledged;
14. terminal/exhausted failure persists quarantine before checkpoint advancement;
15. quarantine persistence failure leaves checkpoint unadvanced;
16. crash after quarantine commit but before checkpoint advance redelivers without handler invocation and can recover checkpoint progress;
17. checkpoint failure after quarantine leaves quarantine immutable and recoverable;
18. route/owner/consumer/tenant rebinding fails closed before attempt execution;
19. same EventID remains independently retryable/quarantinable for distinct legitimate consumer scopes;
