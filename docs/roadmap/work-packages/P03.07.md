# P03.07 — Permission Registration

- Phase: `P03`
- State: `planned`
- Owner/domain: `kernel.modules` with `kernel.authorization` enforcement
- Depends on: `P03.06`
- Blocks: `P03.08`
- Change class: `B`

> Readiness only. `business_feature_code_authorized=false`; permission registration never creates grants by itself.

## Objective

Register stable module-declared permission definitions into the existing deny-by-default authorization foundation while preserving `kernel.authorization` as enforcement/policy authority.

## In scope

- stable permission name/owner/module metadata;
- declaration collision/namespace validation;
- optional capability association and lifecycle availability;
- preservation of policy/role references/history across non-destructive disable/re-enable;
- fail-closed behavior for unknown/unavailable permissions;
- auditability of material registration/lifecycle changes where required.

## Out of scope

- role editor/admin UI;
- new authorization engine or super-admin bypass;
- entitlements/licensing;
- business-domain permission catalogs before their phases.

## Security and architecture invariants

- registration is declaration, never authorization grant;
- server-side capability enforcement remains deny-by-default `kernel.authorization`;
- role names such as admin/owner/superuser never create bypass authority;
- tenant/org scope comes only from trusted P02 context;
- disabled module permissions cannot authorize unavailable behavior;
- uninstall/disable cannot silently destroy historical audit/policy evidence.

## Acceptance criteria

1. valid stable permission declarations register with owner/module identity and deterministic namespace rules.
2. duplicate/conflicting/reserved/invalid permission definitions fail closed.
3. unknown or unavailable module permissions deny rather than allow.
4. registration cannot mutate role grants implicitly or widen principal scope.
5. disable/re-enable preserves safe policy/history semantics while accurately reflecting availability.
6. same-tenant allow and cross-tenant/scope negative tests remain governed by existing P02 authorization behavior.
7. Go quality and P01/P02 regressions pass on GitHub-hosted `ubuntu-24.04`.
