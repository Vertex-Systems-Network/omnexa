# P01.01 — Go Workspace / Build Skeleton

- Phase: `P01`
- State: `planned`
- Owner/domain: `kernel.platform`
- Depends on: `P00.10 done`, `P01 entry gate satisfied`
- Blocks: `P01.02`–`P01.12`
- Change class: `B`

> **Implementation lock:** this package is specification-only while P00.10 remains in exit verification. No executable Go/kernel code is authorized until `docs/roadmap/STATE.json` sets `kernel_code_authorized=true` through the governed P00→P01 transition.

## 1. Objective

Create the minimum reproducible Go workspace/build foundation for Omnexa Kernel without introducing business-domain behavior, persistence, tenancy, module runtime, workflow, or product APIs.

The package establishes a clean source/build boundary, repository-owned Go toolchain declaration, deterministic build/test entry points, a minimal kernel process skeleton suitable for later capabilities, and CI/local evidence that a fresh checkout can compile and execute the package without hidden machine state.

## 2. Why this package exists

Every later kernel capability depends on a stable executable foundation. Starting configuration, storage, telemetry, jobs, identity, modules or domain code before the workspace/build contract exists would cause package-specific build conventions and dependency drift.

P01.01 deliberately creates **structure before behavior**. It is the first executable package after P00 exit because it turns the frozen repository/toolchain/quality contracts into a reproducible implementation lane.

## 3. In scope

- repository-owned Go version declaration consistent with `TOOLCHAIN_STANDARD.md`;
- root Go workspace/module layout required by the modular-monolith architecture;
- `kernel/` executable/library skeleton with no business capability implementation;
- deterministic local commands for format, vet/static baseline, unit tests and build;
- build metadata/version package sufficient to identify source/version without secrets;
- minimal process entrypoint that can start and exit cleanly without external infrastructure;
- baseline test proving the skeleton builds/runs;
- ignore rules for Go build/test artifacts;
- CI integration on the canonical governance lane using any approved Windows/X64 self-hosted runner;
- initial canonical verification wrapper/command mapping for P01.01 applicable gates.

## 4. Out of scope

- environment/configuration system beyond build-time/source metadata (`P01.02`);
- structured application error model implementation (`P01.03`);
- PostgreSQL/migrations (`P01.04`);
- Redis/cache (`P01.05`);
- object/file storage (`P01.06`);
- OpenTelemetry/logging implementation (`P01.07`);
- health/readiness endpoints (`P01.08`);
- jobs/scheduler (`P01.09`);
- feature flags/config registry (`P01.10`);
- audit transport (`P01.11`);
- full developer CLI (`P01.12`);
- HTTP business APIs;
- authentication, tenant lifecycle or organization models (`P02`);
- module runtime (`P03`);
- business modules (`P07+`);
- Docker/Kubernetes production packaging.

## 5. Architecture boundary

- Owning domain/module: `kernel.platform` / repository build foundation.
- Kernel capabilities consumed: none beyond frozen P00 contracts.
- Capabilities provided: deterministic compilation/test/build entrypoints and process/bootstrap boundary only.
- Capabilities consumed: standard Go runtime/library only unless an additional dependency is explicitly justified.
- Events published: none.
- Events consumed: none.
- Workflow actions/triggers: none.
- Data/schema owner: none; this package must not create application database schema.

Initial target source shape may be:

```text
kernel/
├── cmd/
│   └── omnexa/
│       └── main.go
└── internal/
    └── buildinfo/
```

The exact package split may be adjusted during implementation if it remains inside this boundary and does not pre-implement later P01 work packages.

## 6. Tenancy and authorization

Tenancy/authz implementation is **N/A** for P01.01 because no tenant-owned data or protected business capability exists yet.

However:

- no global super-admin/backdoor concept may be introduced;
- no future tenant/authz assumption may be hard-coded into bootstrap structure;
- tests must demonstrate P01.01 contains no business mutation surface;
- later P02 context propagation must be possible without restructuring the whole executable boundary.

## 7. Data model and migrations

- Entities/value objects: none.
- Database ownership: none.
- Migrations: none.
- Fresh-install database path: N/A in P01.01.
- Upgrade/backfill path: N/A.
- Retention/audit: N/A.

The package must fail review if it introduces database drivers, migration files or domain schemas not required by the build skeleton.

## 8. API / event / contract changes

No public business API or domain event is introduced.

Implementation may expose only internal build/version metadata such as:

- semantic/source version;
- commit SHA when injected by build tooling;
- build timestamp only if reproducibility policy permits it;
- dirty-tree indicator only when deterministic semantics are defined.

No metadata may contain secrets, local usernames, absolute workstation paths or credentials.

## 9. Failure and recovery behavior

- compiler/build failure returns non-zero;
- test failure returns non-zero;
- missing required pinned toolchain fails clearly;
- no dependency on running PostgreSQL/Redis/NATS/S3 is allowed;
- process startup must not hang waiting for infrastructure not owned by this package;
- process shutdown/exit must be deterministic;
- retry/duplicate/replay semantics are N/A.

## 10. Observability

P01.07 owns structured logging/OpenTelemetry, so P01.01 must not invent a competing observability framework.

Allowed evidence:

- deterministic CLI/build output;
- test output;
- process exit code;
- build metadata display only where explicitly designed.

No production telemetry contract is frozen by this package.

## 11. Security considerations

- no secrets committed or embedded in binary defaults;
- no network listener exposed unless explicitly required by a later package;
- no shelling out to unpinned remote installers during build;
- dependencies must have explicit provenance/license metadata under P00.07/P00.08 policy;
- build scripts must not execute arbitrary downloaded code;
- generated/version metadata must not leak local paths or credentials;
- P00 threat model items related to supply chain and build integrity apply.

## 12. Acceptance criteria

1. **AC-01** — A clean checkout with the repository-declared Go toolchain can execute the canonical P01.01 verification commands without undocumented setup.
2. **AC-02** — The Go workspace/module graph contains only kernel/build-skeleton scope and has no business-domain package.
3. **AC-03** — `go test` for the P01.01 scope passes from zero.
4. **AC-04** — formatting/vet/static checks required by the initial Go quality profile pass.
5. **AC-05** — the Omnexa kernel skeleton builds successfully on the canonical CI lane and at least the canonical Linux-compatible Go target is not structurally blocked by Windows-only code.
6. **AC-06** — the built process starts/exits deterministically without PostgreSQL, Redis, NATS or object storage.
7. **AC-07** — build/version metadata is reproducible enough to identify source commit/version and contains no secret/local-path leakage.
8. **AC-08** — no database schema/migrations, tenant/authz implementation, module runtime or business functionality is introduced.
9. **AC-09** — applicable G0/G1/G2/G7 checks produce `PASS` evidence through the required `governance` lane on an approved Windows/X64 runner; blocked/not-run evidence is not accepted as PASS.
10. **AC-10** — `STATE.json`, `STATUS.md` and execution ledger are reconciled only after executable acceptance passes.

## 15. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Overbuilding the skeleton | Later packages become pre-coupled | Enforce explicit out-of-scope list and dependency review |
| Toolchain drift | Local/CI mismatch | Single repository-owned version declaration and clean-checkout test |
| Windows-specific assumptions | Linux/server portability failure | No Windows-only kernel code; add Linux portability evidence before P01 exit |
| Early third-party dependency sprawl | Supply-chain/license risk | Standard library first; each added dependency justified and reviewed |
| CLI/build wrapper becomes architecture | Hard future migration | Keep semantic commands stable while implementation wrapper remains replaceable |
| Hidden local state | Non-reproducible builds | Fresh checkout and no-external-infra acceptance tests |
