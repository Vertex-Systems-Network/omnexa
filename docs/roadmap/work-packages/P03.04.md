# P03.04 — Module Lifecycle State Machine

- Phase: `P03`
- State: `active`
- Owner/domain: `kernel.modules`
- Depends on: `P03.03`
- Blocks: `P03.05`
- Change class: `B`

> P03.04 is the sole active package after the governed P03.03 completion transition merges. `kernel_code_authorized=true` is bounded to P03.04 lifecycle implementation only; `business_feature_code_authorized=false` remains unchanged. P03.05+ remains planned/locked.

## Objective

Implement explicit dependency-aware install/enable/disable/suspend/archive/detach/purge plus upgrade/re-enable lifecycle semantics that are idempotent/retry-aware, observable and safe for unrelated modules.

## In scope

- explicit lifecycle states and allowed transitions;
- dependency preconditions and reverse-dependency protection;
- non-destructive disable/re-enable semantics;
- suspend/archive/detach distinctions and historical-state preservation;
- explicit authorized audited purge semantics;
- upgrade transition coordination with owned migration metadata;
- concurrency/duplicate-request protection and retry/idempotency rules;
- partial-failure handling with deterministic recovery/forward-fix state.

## Out of scope

- module-specific settings/capability/permission/UI registry behavior beyond lifecycle availability hooks;
- marketplace trust/sandboxing;
- P04 durable event/workflow orchestration;
- P03.05+ implementation;
- business-feature implementation;
- strategic X-program runtime;
- AI/model/agent runtime.

## Security and architecture invariants

- disable never silently erases owned business/audit evidence;
- purge is destructive, explicit, dependency-checked, authorization-gated and auditable;
- required dependency failures fail closed before invalid activation;
- lifecycle mutation cannot bypass tenant/authorization/audit foundations;
- concurrent/retried lifecycle operations cannot double-apply migrations/destructive effects;
- failure in one module cannot corrupt unrelated module state where isolation is feasible.

## Acceptance criteria

1. transition table rejects invalid state transitions deterministically.
2. install/enable requires a valid dependency graph; reverse dependencies protect destructive detach/purge.
3. disable/re-enable reference behavior is non-destructive and repeatable.
4. repeated/concurrent lifecycle requests preserve a single valid state and explicit outcome.
5. purge tests prove explicit authorization/audit/dependency protection and no silent evidence erasure.
6. failure fixtures preserve recoverable state and unrelated module integrity.
7. upgrade lifecycle can coordinate with the later P03.09 migration ownership contract without owning migration execution prematurely.
8. Go quality and all P01/P02/P03.01/P03.02/P03.03 regressions pass on canonical GitHub-hosted `ubuntu-24.04`.
9. no P03.05+ implementation is added.
