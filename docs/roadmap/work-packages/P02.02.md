# P02.02 — Tenant Lifecycle & Trusted Tenant Context

- Phase: `P02`
- State: `planned`
- Owner/domain: `kernel.tenancy`
- Depends on: `P02.01`
- Blocks: `P02.03`–`P02.10`
- Change class: `B`

> `kernel_code_authorized=false` and `business_feature_code_authorized=false` at readiness time.

## Objective

Implement the primary tenant isolation boundary and trusted tenant execution context before organization or business data depends on it.

## In scope

- authoritative Tenant identity/lifecycle/state under `kernel.tenancy`;
- canonical `tenant_id` persistence semantics where tenant-owned state applies;
- trusted tenant context derived from authenticated/execution relationships rather than request payload authority;
- tenant relationship/membership primitive only to the minimum needed for later scoped authorization;
- explicit cross-tenant privileged boundary contract without implementing support superuser bypass;
- tenant-safe persistence/query helpers that make missing scope difficult;
- same-tenant positive and cross-tenant negative tests;
- fresh/upgrade migration evidence for persistence changes.

## Out of scope

- organization hierarchy (`P02.03`);
- authentication/session implementation (`P02.04`);
- roles/policy (`P02.05-P02.06`);
- tenant business data, customer/employee records, modules or business features;
- hidden cross-tenant administrator access.

## Security and architecture invariants

- client-provided tenant IDs are never authorization authority;
- tenant isolation applies independently of data classification;
- cross-tenant operations require explicit capability/policy and audit when later exposed;
- no global-tenant fallback;
- owner is `kernel.tenancy`.

## Acceptance criteria

1. Tenant lifecycle and identifiers are deterministic and owner-bounded.
2. trusted context cannot be forged by changing an input tenant ID.
3. same-tenant operations succeed while cross-tenant equivalents fail closed.
4. persistence/query surfaces require explicit tenant scope where applicable.
5. no organization/RBAC/business behavior is pulled forward.
6. fresh + supported-upgrade migrations pass if schema changes.
7. P01 and P02.01 regressions plus Go quality remain green.
8. applicable G0-G8 evidence runs on canonical GitHub-hosted `ubuntu-24.04`.

## Completion evidence

Record exact PR/head/run/job and tenant-isolation/migration/security evidence only after observed execution.

## State transition

`planned -> active -> verification -> done`. Only a separate closure may activate P02.03.
