## Security and architecture invariants

- manifest/package metadata is untrusted input;
- parser work remains bounded before deeper decoding;
- schema-v1 behavior cannot be silently reinterpreted;
- unsupported/malformed schema versions fail closed;
- schema-v2 dependency records reject unknown fields, invalid IDs/constraints, duplicates, self-dependencies and cross-class conflicts;
- circular required dependencies are release-blocking invalid state;
- missing/incompatible required dependency fails closed;
- optional absence/incompatibility cannot make unrelated modules fail globally;
- optional edges do not create required install/enable ordering authority or participate in the required global cycle gate;
- resolver input is provenance-bound to the exact validated discovery snapshot;
- a registry/manifest snapshot association mismatch or missing snapshot fails closed;
- public P03.02 one-record-per-ID semantics remain unchanged;
- no resolver path grants capability, permission, tenant or database authority;
- kernel may not depend on business modules and direct cross-module private imports/writes remain forbidden;
- resolution is deterministic for identical validated discovery state;
- no parser/discovery/resolver path executes module code or performs unapproved filesystem/network access.

## Constraint grammar

Schema-v2 module dependency constraints use the accepted ADR-0012 grammar:

- 1–16 comparators;
- maximum 256 encoded bytes;
- exactly one ASCII space between comparators;
- no leading/trailing whitespace;
- operators `=`, `>`, `>=`, `<`, `<=`;
- strict SemVer 2.0.0 operands;
- logical AND across comparators;
- no OR, wildcard, caret, tilde, comma-separated or implicit/package-manager range syntax;
- SemVer precedence controls comparison and equality;
- build metadata does not affect precedence.

## Schema-v1 compatibility

- v1 manifests remain parseable under the retained P03.01 contract;
- v1 manifests with no module dependencies remain resolver-eligible subject to all other gates;
- v1 manifests with required module dependencies fail closed for install/enable eligibility until migrated to v2 because no per-dependency version contract exists;
- v1 optional module dependency declarations produce explicit unresolved/degraded optional metadata until migrated;
- v1 strings are never inferred as unconstrained, same-major or latest-compatible declarations.

## Registry and graph semantics

- one discovered module ID maps to at most one discovered version;
- multi-version/SAT solving is excluded;
- each public registry identity is atomically associated with one internal normalized validated manifest snapshot;
- required compatibility compares the discovered module version against the declaring module's explicit constraint from its bound snapshot;
- required edges alone determine deterministic topological order;
- required cycles are invalid;
- optional edges are evaluated independently and do not create global required-cycle failure;
- forbidden/private dependency checks remain orthogonal to version compatibility.
