# P03.03 — Dependency Graph Resolver

- Phase: `P03`
- State: `active`
- Owner/domain: `kernel.modules`
- Depends on: `P03.02`
- Blocks: `P03.04`
- Change class: `B`
- Class C prerequisite: accepted `ADR-0012 — Versioned Module Dependency Requirements`

> P03.03 is the sole active package on protected main. The accepted ADR-0012 reconciliation becomes authoritative when its accepting PR merges. P03.03 implementation must then start from that exact protected-main SHA in a separate implementation branch. `kernel_code_authorized=true` remains bounded to P03.03 only and `business_feature_code_authorized=false` remains unchanged.

## Objective

Implement deterministic module dependency validation/resolution that machine-enforces `MODULE_STANDARD.md`, `DEPENDENCY_MATRIX.md` and accepted ADR-0012 required, optional, platform, forbidden and version-compatibility semantics.

## Accepted prerequisite contract

P03.03 owns the forward implementation required by ADR-0012 without reopening historical P03.01/P03.02 completion:

- explicit bounded manifest schema-version dispatch;
- preserved strict schema-v1 parsing/validation behavior;
- separate strict schema-v2 parsing/validation;
- schema-v2 required/optional dependencies represented as exact `{id, constraint}` records;
- strict bounded SemVer comparator grammar;
- additive package-private normalized validated-manifest binding during discovery;
- resolver declarations sourced only from the exact registry-bound validated snapshot;
- public P03.02 one-record-per-module-ID/list/lookup semantics preserved.

## In scope

- explicit schema-version dispatch for v1/v2 with no parser fallback;
- schema-v2 structured required/optional module dependency requirements;
- strict SemVer version/constraint parsing and comparison under ADR-0012 bounds;
- version-aware required and optional dependency resolution;
- platform dependency validation;
- package-private discovery binding between each registry identity and its exact normalized validated manifest snapshot;
- deterministic topological order for valid required graphs;
- self-dependency, required-cycle and incompatible-version detection;
- undeclared/forbidden/private dependency detection hooks that can be proven by reference fixtures;
- selective optional-dependency degradation metadata for later lifecycle/capability availability decisions;
- explicit schema-v1 compatibility/degradation behavior defined by ADR-0012;
- stable safe deterministic validation/resolution diagnostics;
- dedicated P03.03 verifier and canonical GitHub-hosted governance wiring.

## Out of scope

- lifecycle mutations;
- package installation/download;
- remote marketplace/catalog lookup;
- multi-version/SAT dependency solving;
- automatic dependency upgrade/downgrade selection;
- external compatibility matrix;
- separately reparsed raw-manifest resolver input;
- P04 event dependency orchestration;
- full System Graph runtime or trust/advisory scanning;
- P03.04+ implementation;
- business-feature behavior;
- AI/model/agent runtime.

## Security and architecture invariants

- manifest/package metadata is untrusted input;
- parser work remains bounded before deeper decoding;
- schema-v1 behavior cannot be silently reinterpreted;
- unsupported/malformed schema versions fail closed;
- schema-v2 dependency records reject unknown fields, invalid IDs/constraints, duplicates, self-dependencies and cross-class conflicts;
- circular required dependencies are release-blocking invalid state;
- missing/incompatible required dependency fails closed;
- optional absence/incompatibility cannot make unrelated modules fail globally;
- optional edges do not create required install/enable ordering authority or participate in the required global cycle gate;
- resolver input must be provenance-bound to the exact validated discovery snapshot;
- a registry/manfiest snapshot association mismatch or missing snapshot fails closed;
- public P03.02 one-record-per-ID semantics remain unchanged;
- no resolver path grants capability, permission, tenant or database authority;
- kernel may not depend on business modules and direct cross-module private imports/writes remain forbidden;
- resolution is deterministic for identical validated discovery state;
- no parser/discovery/resolver path executes module code or performs unapproved filesystem/network access.

## Constraint grammar

Schema-v2 module dependency constraints use the accepted ADR-0012 grammar:

- 1–16 comparators;
- maximum 256 encoded bytes;
- exactly one ASCII space between comparators;
- no leading/trailing whitespace;
- operators `=`, `>`, `>=`, `<`, `<=`;
- strict SemVer 2.0.0 operands;
- logical AND across comparators;
- no OR, wildcard, caret, tilde, comma-separated or implicit/package-manager range syntax;
- SemVer precedence controls comparison and equality;
- build metadata does not affect precedence.

## Schema-v1 compatibility

- v1 manifests remain parseable under the retained P03.01 contract;
- v1 manifests with no module dependencies remain resolver-eligible subject to all other gates;
- v1 manifests with required module dependencies fail closed for install/enable eligibility until migrated to v2 because no per-dependency version contract exists;
- v1 optional module dependency declarations produce explicit unresolved/degraded optional metadata until migrated;
- v1 strings are never inferred as unconstrained, same-major or latest-compatible declarations.

## Registry and graph semantics

- one discovered module ID maps to at most one discovered version;
- multi-version/SAT solving is excluded;
- each public registry identity is atomically associated with one internal normalized validated manifest snapshot;
- required compatibility compares the discovered module version against the declaring module's explicit constraint from its bound snapshot;
- required edges alone determine deterministic topological order;
- required cycles are invalid;
- optional edges are evaluated independently and do not create global required-cycle failure;
- forbidden/private dependency checks remain orthogonal to version compatibility.

## Acceptance criteria

1. schema-version dispatch is bounded, deterministic and uses separate strict v1/v2 decoders with no fallback.
2. retained P03.01 schema-v1 fixtures remain green where historical semantics are unchanged.
3. schema-v2 `{id, constraint}` dependency records validate deterministically, including unknown-field, duplicate, self-dependency, cross-class and resource-bound negative cases.
4. strict SemVer comparison covers exact/lower/upper bounds, prerelease ordering, invalid prerelease forms, build-metadata precedence equality and malformed constraints.
5. required dependency presence/version is enforced before install/enable eligibility.
6. optional absence/incompatibility produces explicit selective-degradation data rather than global failure.
7. registry-to-normalized-manifest binding is atomic; missing/mismatched/mutable associations fail closed and a second raw-manifest input cannot drive resolver policy.
8. public P03.02 lookup/list/cardinality, duplicate-ID and version-conflict behavior remains unchanged.
9. required cycles, incompatible constraints and undeclared/forbidden/private dependency fixtures are rejected deterministically.
10. optional-cycle fixtures prove optional edges do not globally invalidate a valid required graph.
11. valid required graph produces stable ordering independent of discovery enumeration order.
12. schema-v1 required/optional dependency-bearing behavior matches ADR-0012 migration/degradation rules.
13. no resolver path grants authority or accesses another module's private schema/package.
14. dedicated `scripts/verify_p03_03.sh` passes together with repository Go quality and all retained P01/P02/P03.01/P03.02 regressions on GitHub-hosted `ubuntu-24.04`.
15. implementation evidence binds to the exact final implementation head.

## Implementation discipline

- no external SemVer/constraint dependency is introduced without separate dependency-introduction justification covering license, security/supply-chain, maintenance, deployment burden and exit strategy;
- do not weaken historical verifiers to make new code pass; narrow stale future-scope guards only when the newly accepted P03.03 contract makes that necessary and preserve equivalent historical invariants;
- stable diagnostic codes must not echo raw untrusted manifest content;
- any discovery internal extension must preserve public P03.02 behavior;
- implementation PR must not change canonical package state to `done` or activate P03.04.
