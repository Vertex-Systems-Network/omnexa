- State: `prepared / planned / locked`
- Owner/domain: `kernel.events`

## Objective

Define the minimum provider-neutral contract for identifying event payload schemas, registering immutable historical versions, evaluating deterministic compatibility, and validating an event payload **before protected handler mutation**.

P04.07 must preserve the accepted event-fabric boundaries rather than redefining them:

- P04.01 remains authoritative for the canonical event envelope, EventID, event type identity and envelope version;
- P04.07 adds an explicit **payload schema version** for the stable P04.01 event type identity and must not overload or reinterpret the P04.01 envelope version;
- P04.02 remains authoritative for producer/route/consumer registration and ownership;
- P04.03 checkpoint, P04.05 inbox/idempotency and P04.06 retry/quarantine state remain separate facts;
- schema validation proves only that a payload conforms to an accepted contract version. It does **not** authorize a protected action, prove exactly-once processing, grant cross-module write authority, or establish global ordering.

This package closes the event-payload contract identity/compatibility/validation boundary only. It does not change background-job ownership/execution (`P04.08`), broad operator/reliability recovery (`P04.09`), controlled replay/poison-event aggregate acceptance (`P04.10`), or any business feature/module.

## Retained authority and architecture

P04.07 must reuse existing foundations rather than create parallel authority:

- canonical EventID, event type identity and envelope semantics remain P04.01 authority;
- producer/route/consumer ownership and accepted route binding remain P04.02 authority;
- checkpoint progress remains P04.03 authority;
- outbox publication remains P04.04 authority;
- protected local duplicate-safe mutation/inbox completion remain P04.05 authority;
- retry, terminal failure, quarantine and retry claim/lease semantics remain P04.06 authority;
- stable safe structured failures remain P01.03 authority;
- tenant/org authorization and capability enforcement remain accepted P02/P03 authority;
- migration execution/ledger/advisory-lock authority remains the retained P01 migration runner and P03.09 owner declarations;
- audit/observability/data-classification rules remain their accepted P01/P02 authorities.

No schema ID, schema version, schema fingerprint, compatibility result, validation result, registry row, producer identity, tenant identifier, route identity or provider receipt grants authorization.

## Payload-schema identity law

P04.07 schema identity must be bound to a stable accepted event contract identity rather than transient transport metadata.

The minimum logical identity is:

- stable P04.01 event type identity;
- authoritative owner/module identity;
- explicit positive payload schema version;
- accepted producer/route binding where required to prevent ambiguous rebinding.

Requirements:

1. the payload schema version is a separate field/concept from the P04.01 envelope version and must never redefine the envelope contract;
2. provider topic/subject names, broker message IDs, offsets, delivery tags or transient aliases must not become canonical schema identity;
3. one exact `(owner, event type, payload schema version)` identity maps to one immutable accepted schema fingerprint;
4. re-registering the same identity with different canonical schema content fails closed as a conflict;
5. the same stable event type/version must mean the same payload contract across tenants; tenant-controlled per-tenant contract forks are forbidden unless a later separately governed contract explicitly authorizes them;
6. owner/producer/route rebinding must fail before handler mutation;
7. caller-controlled aliases must not select a different schema for an already-accepted event identity;
8. unknown, malformed, zero/negative, unsupported or unregistered payload schema versions fail closed.

The exact wire field carrying payload schema version is a later implementation detail and must be introduced compatibly with the accepted P04.01 envelope extension rules. This preparation does not mutate the P04.01 envelope or reserve a field name.

## Immutable historical schema law

Accepted historical schema versions are immutable evidence.

A later implementation must enforce:

- accepted schema bytes/normalized representation are never edited in place after acceptance;
- a contract change receives a new explicit payload schema version;
- deleting or replacing an accepted historical version is not an ordinary runtime operation;
- historical fingerprints remain queryable enough to detect conflicting identity/content reuse;
- policy changes do not retroactively rewrite whether an already-accepted schema version existed;
- rollback/forward recovery must not silently remap an old schema version to new semantics.

If later retention or archival is required, it must preserve enough immutable identity/fingerprint evidence to reject conflicting reuse for every still-supported historical version.

## Deterministic canonical fingerprint law

Every accepted schema version must have a deterministic canonical fingerprint.

The later implementation must define and freeze, before runtime acceptance:

- the supported schema representation/dialect or bounded subset;
- the exact canonicalization/normalization procedure;
- the exact cryptographic digest algorithm and encoding;
- treatment of insignificant formatting/order where the chosen representation permits it;
- maximum accepted schema size/depth/complexity;
- rejection rules for unsupported constructs.

Requirements:

1. identical logical accepted schema content under the defined canonicalization yields the same fingerprint;
2. materially different accepted schema content cannot share one schema identity merely because caller metadata matches;
3. raw transport/provider metadata is excluded from the canonical schema fingerprint unless explicitly part of the accepted schema contract;
4. canonicalization must be deterministic, bounded and free of network access or dynamic code execution;
5. the fingerprint is integrity/identity evidence only and is not an authorization credential.

This preparation intentionally does **not** select JSON Schema, Avro, Protobuf, Confluent Schema Registry or another schema technology. A later implementation decision must remain provider-neutral and prove the chosen bounded representation satisfies these laws.

## Registration and ownership law

Schema registration is an owner-governed control-plane action, not a producer- or tenant-selected runtime shortcut.

Minimum requirements:

- only the authoritative event owner may propose/register a new schema version through the accepted capability/change boundary;
- producer identity must be bound to the accepted P04.02 route/ownership declaration before it may emit a schema-versioned event;
- tenant input cannot create, mutate, shadow or override the registry contract;
- ordinary event delivery cannot auto-register an unknown schema;
- first registration of a new event type/version must be explicit and deterministic;
- concurrent registration of the same exact identity/content may converge safely, but conflicting content must fail closed;
- registry mutation must produce bounded safe structured evidence suitable for audit/diagnostics without leaking restricted schema examples or secrets;
- no schema registration may create cross-module private-table write authority or bypass package ownership.

A later public/admin API, if any, requires separate capability/authorization/audit design. This preparation does not authorize one.

## Compatibility policy law

Compatibility must be explicit, deterministic and bound to a stable policy mode. Compatibility is not inferred from prose, naming conventions or provider defaults.

The V1 contract recognizes these logical modes:

- `backward` — a consumer using the candidate/new schema version must be able, under the accepted bounded compatibility rules, to accept payloads valid under the required predecessor set;
- `forward` — a consumer using the required predecessor schema set must be able, under the accepted bounded compatibility rules, to accept payloads valid under the candidate/new schema version;
- `full` — both backward and forward compatibility must pass;
- `exact` — only canonically fingerprint-identical schema content is compatible.

Direction/mode semantics must be implemented against an explicitly declared predecessor comparison set. A later implementation must choose and document whether that set is the immediately previous accepted version or a bounded retained history set; it must not silently change this rule at runtime.

Compatibility requirements:

1. the same candidate schema, predecessor set and policy mode always produce the same result;
2. compatibility evaluation operates only on the locally available accepted schema representations and never fetches remote references;
3. unsupported/ambiguous constructs fail closed rather than being guessed compatible;
4. compatibility must be evaluated **before** accepting a new schema version as registered history;
5. failure must return a stable bounded machine reason; raw parser/runtime/provider text is not public contract evidence;
6. a policy mode change is itself a governed owner decision and applies prospectively; it does not retroactively rewrite accepted history;
7. a less strict future policy cannot silently make a previously rejected conflicting same-version registration valid;
8. no compatibility result authorizes event publication, protected handling or cross-tenant access;
9. compatibility does not prove semantic/business equivalence beyond the formally supported schema rules;
10. provider defaults must never override the Omnexa compatibility contract.

A later implementation may expose a narrow provider-neutral `CompatibilityPolicy` / `CompatibilityResult` seam. Arbitrary transport adapters must not redefine compatibility semantics.

## Bounded local-reference law

P04.07 V1 must be deterministic and locally evaluable.

Therefore:

- remote HTTP(S), registry-to-registry, filesystem escape, DNS or network schema/reference fetching is forbidden;
- dynamic code loading/execution, eval, arbitrary plugin execution, shell execution or schema-supplied callbacks are forbidden;
- cyclic/unbounded reference traversal must be rejected or bounded deterministically;
- if local references are supported later, they must resolve only within the exact accepted owner/version registry graph under explicit depth/count/size limits;
- missing or conflicting references fail closed;
- referenced schemas remain immutable/versioned and fingerprint-bound;
- no schema or reference may derive authorization rules, capabilities, tenant membership, secrets or executable business policy.

This law prevents registry validation from becoming an implicit remote code/configuration execution system.

## Payload validation law

Payload validation must occur after canonical envelope/route identity has been established and before any protected handler mutation.

Minimum processing order:

1. accept/validate the P04.01 envelope and stable event identity under retained authority;
2. establish authoritative owner/producer/route binding under P04.02;
3. resolve the exact registered payload schema identity/version from local accepted registry state;
4. fail closed on unknown/unregistered/unsupported identity or version;
5. validate payload against the exact immutable schema version with bounded deterministic limits;
6. only a successful validation result may reach the protected handler/mutation boundary;
7. authorization/business preconditions are still evaluated independently at the actual protected action boundary;
8. P04.05 inbox and P04.06 retry/quarantine compose under their own accepted rules and are not replaced by schema validation.

Validation requirements:

- malformed/invalid payload never reaches protected mutation;
- validation errors are stable, bounded, safe and path-limited; they must not dump unrestricted confidential/restricted payload content;
- validator CPU/time/memory/depth/collection limits must be explicit before runtime acceptance;
- unknown or unsupported schema constructs fail closed;
- validation must be deterministic for the same schema fingerprint and payload bytes/logical value under the chosen representation;
- validation success is not cached/reused across conflicting event/schema identities without exact binding evidence;
- validation failure must not create a fake P04.05 inbox completion, checkpoint success or business-success result;
- the P04.06 failure-disposition boundary remains authoritative for retry/quarantine consequences once P04.07 is later active; P04.07 must not invent a parallel retry ledger.

Ordinary schema-invalid/unregistered-contract results are expected to be stable non-success outcomes, but their exact P01.03/P04.06 failure mapping is a later implementation decision that must be explicit and testable.

## Tenant, owner and producer isolation law

The registry is an owner-governed contract registry, not a tenant customization store.

A later implementation must prove:

- one tenant cannot register, mutate, shadow, enumerate unauthorized owner-private metadata, or select a different contract for another tenant;
- the same accepted event type/version retains one canonical schema fingerprint across tenants;
- owner scope is mandatory and cannot be replaced by a caller-provided label;
- producer identity/route must match accepted P04.02 declarations before schema-versioned publication/handling is accepted;
- consumer validation cannot use a producer-controlled registry endpoint or remote reference;
- cross-owner same-name event types cannot collide if their accepted canonical identity is distinct;
- registry diagnostic reads remain capability/tenant/owner bounded as applicable;
- no tenant-specific schema fork is introduced by this package.

If a future product requirement needs tenant-specific extension contracts, it requires a separate governed architecture decision and cannot be smuggled into P04.07 V1.

## Checkpoint, inbox, retry and schema separation

Four facts remain distinct:

1. P04.03 checkpoint = ordered durable consumption progress.
2. P04.05 inbox completion = duplicate-safe protected local mutation evidence.
3. P04.06 retry/quarantine = failure disposition, attempt budget, eligibility and terminal poison-event evidence.
4. P04.07 schema registry/validation = payload contract identity, compatibility and validation evidence.

Consequences:

- a schema registration does not advance a checkpoint;
- validation success does not create inbox completion;
- validation failure does not itself create quarantine state; later P04.06 composition owns retry/quarantine persistence;
- quarantine does not make an invalid payload schema-valid;
- an already-applied inbox outcome does not authorize changing the historical schema identity of that event;
- checkpoint position cannot be used as proof of schema registration;
- none of these facts grants authorization or proves exactly-once/global ordering.

## Security, privacy and observability law

- registry/schema diagnostics must follow accepted data classification and P01.03/P01.07 safe-error/logging rules;
- confidential/restricted payload examples must not be copied into registry errors, compatibility reports or metrics;
- secrets, credentials, tokens, raw database/provider errors and unrestricted stack traces are prohibited from persisted/public validation evidence;
- safe telemetry may include bounded owner/event-type identifiers where policy allows, schema version, compatibility mode/result code, validator result code and duration buckets;
- high-cardinality raw EventID/tenant/user identifiers must not be blindly used as metric labels;
- schema fingerprints are integrity identifiers, not secrets, permissions or audit substitutes;
- registry mutation and privileged inspection may require P01.11 audit evidence in the later authorized implementation;
- validation must not deserialize into executable types in a way that triggers arbitrary constructors/hooks/code.
