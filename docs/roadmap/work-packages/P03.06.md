## Objective

Create a versioned owner-aware registry for module-provided and consumed capabilities using `MODULE_STANDARD.md` capability semantics so later modules, workflows, federation and AI can discover governed boundaries without private implementation coupling.

## Authorized scope after activation merge

- stable capability ID and major version metadata;
- provider module/owner and consumer declarations;
- lifecycle-derived availability state;
- authorization/tenant-org scope requirement metadata and contract references;
- collision/version compatibility validation;
- lifecycle-aware registration/withdrawal availability;
- deterministic lookup suitable for later attribution/graph consumers;
- focused positive/adversarial tests;
- a dedicated P03.06 verifier and canonical governance wiring after retained P03.05 verification.

## Security and architecture invariants

- registration does not grant permission to call a capability;
- owning capability boundary remains responsible for validation/authorization/audit;
- registry lookup cannot bypass trusted tenant/org scope or `kernel.authorization`;
- registry does not expose private handlers, private implementation objects, database tables, credentials, secrets or restricted values;
- duplicate/conflicting owner + capability + major-version definitions fail closed;
- disabled/unhealthy/unavailable providers cannot be reported as active capability;
- lifecycle state is availability input only and grants no permission/capability authority;
- registry metadata cannot create cross-module database write authority;
- stable identifiers support later XSG/XPF/XPERF consumers without making those programs dependencies or activating them;
- P03.05 settings/feature flags cannot be used as hidden authority for capability invocation.

## Acceptance criteria

1. provided/consumed capability declarations register and resolve deterministically by stable ID/version/owner.
2. duplicate/conflicting owner/version definitions are rejected.
3. lifecycle state changes update availability without deleting historical identity needed for audit/reference.
4. authorization and scope requirements are represented but cannot be bypassed through registry lookup.
5. tests prove no private implementation/database coupling is required for discovery.
6. compatibility/version fixtures cover supported and incompatible major versions.
7. Go quality plus all retained P01/P02/P03.01-P03.05 regressions pass on GitHub-hosted `ubuntu-24.04`.
8. a dedicated P03.06 verifier pins the material authority/isolation/version/lifecycle invariants.
9. no P03.07+ or business-feature runtime is introduced.
