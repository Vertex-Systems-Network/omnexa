## Objective

Create a versioned owner-aware registry for module-provided and consumed capabilities using validated discovery snapshots and accepted lifecycle state so later governed consumers can discover stable capability boundaries without private implementation coupling or implicit invocation authority.

## Accepted P03.06 registry design

P03.06 does **not** change manifest schema v1 or v2. Existing `capabilities_provided` / `capabilities_consumed` declarations remain bounded manifest identifiers. The package-private validated manifest snapshot now retains copied validated capability declarations so the capability registry consumes exactly the same validated discovery provenance that created module identity; raw manifests are not reparsed independently to create capability authority.

Capability declarations such as `inventory.reserve-stock.v1` are normalized into stable capability identity plus a positive bounded major version. Provider registration remains bound to the discovered module ID and owner. Consumer declarations resolve deterministically against compatible stable capability ID + major version.

Registration accepts only explicit descriptive metadata references for authorization requirements, trusted tenant/organization scope requirements and public contracts. Those references describe prerequisites; they do not grant access, create raw tenant/org scope, expose handlers, or become an invocation interface.

Provider availability is derived from the accepted P03.04 lifecycle state. Only `LifecycleEnabled` providers are runtime available. Disabled, suspended, archived, detached, recovery-required, purged or merely discovered/available providers are not reported active. Static/historical identity remains retained so lifecycle transitions do not silently destroy discovery/audit/reference semantics.

The registry rejects undeclared registrations, module/owner mismatches, duplicate/conflicting capability+major providers and incompatible major-version resolution fail closed. It exposes no private handler/function object, package-private implementation, database table, credential, secret, restricted value, permission grant, raw tenant identifier or cross-module write authority.

## Security and architecture invariants

- capability registration and lookup are metadata/availability only and never grant permission to invoke a capability;
- owning capability boundaries remain responsible for validation, authorization, trusted tenant/org enforcement and required audit;
- registry lookup cannot bypass `kernel.authorization` or trusted P02 tenant/organization context;
- registry records expose no private handlers, implementation objects, raw database tables, credentials, secrets or restricted values;
- duplicate/conflicting owner + capability + major-version definitions fail closed;
- unavailable lifecycle states cannot be represented as active merely because a declaration exists;
- lifecycle state is an availability input only and grants no capability or permission authority;
- registry metadata creates no cross-module database write authority;
- P03.05 settings/feature flags remain non-authorizing and cannot be used as hidden capability invocation authority.
