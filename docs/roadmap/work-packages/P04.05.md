- State: `prepared / planned / locked`
- Owner/domain: `kernel.events`

- Blocks: `P04.06`

No P04.05 runtime, schema, migration, business-handler, retry/DLQ, provider, job-runtime or state mutation may begin until a later separate governance/state/continuity transaction records P04.04 done, explicitly accepts this contract, makes P04.05 the sole active package, passes exact-head Omnexa Governance, merges through the protected path, and protected `main` is re-read.

## Objective

Define the minimum provider-neutral consumer inbox/deduplication and application-idempotency boundary required to make duplicate delivery safe for one protected consumer application against local PostgreSQL state.

P04.05 must preserve the accepted P04.03/P04.04 truth that duplicate delivery/publication can occur. It must not hide duplicates by claiming transport-level or end-to-end exactly-once semantics. Instead, a protected consumer must use stable canonical event identity plus stable consumer/owner/tenant scope so that the **same accepted event cannot apply the same protected local mutation twice**.

This package closes the local duplicate-redelivery-to-business-mutation window only. It does not define retry/backoff or DLQ policy (P04.06), schema-registry runtime (P04.07), background-job execution (P04.08), operator recovery UX (P04.09), or the terminal aggregate failure/replay package (P04.10).

## Retained authority and architecture

P04.05 must compose accepted foundations rather than create parallel ones:

- canonical event identity and validated envelope remain P04.01 authority;
- stable producer/route/consumer registration and ownership remain P04.02 authority;
- durable consumer/checkpoint and duplicate-redelivery semantics remain P04.03 authority;

- authorization remains at the actual protected action boundary under accepted P02/P03 rules.

No inbox row, dedup key, checkpoint, EventID, consumer identity or transport receipt grants authorization or cross-module write authority.

## Stable consumer-processing identity law

Deduplication must be scoped narrowly enough that two legitimate consumers can independently process the same canonical event while one consumer cannot apply it twice.

The minimum logical processing identity is the tuple of:

- canonical P04.01 `EventID`;
- stable accepted consumer/handler registration identity from the P04.02/P04.03 boundary;
- authoritative owner/module scope;
- trusted tenant scope where the consumer is tenant-scoped;
- route/event-type identity where required to prevent ambiguous rebinding.

Requirements:

- EventID alone must not become a global cross-consumer lock;
- caller-controlled aliases must not be able to rebind an already-seen event to another owner/tenant/consumer;
- an exact same canonical event re-delivered to the same processing scope is a duplicate candidate, not a new mutation request;
- reuse of the same processing identity with conflicting canonical envelope identity/content must fail closed;
- provider offsets, broker message IDs or transient delivery IDs may be diagnostic evidence but must not replace canonical identity.

## Inbox and protected-mutation atomicity law

For a local PostgreSQL protected mutation whose duplicate application would be unsafe, the inbox/dedup acceptance record and the protected mutation must share the same local database transaction.

A later authorized implementation must prove:

1. authorization/business preconditions are evaluated under their existing authoritative boundaries before a protected mutation is committed;
2. the consumer transaction establishes the processing identity inside the **same local PostgreSQL transaction** as the protected mutation;
3. a first valid delivery may apply the protected mutation and persist a durable completion/dedup record atomically;
4. mutation failure rolls back the inbox/dedup completion record;
5. inbox/dedup persistence failure prevents the protected mutation from committing;
6. after commit, later delivery of the same processing identity returns an explicit already-applied/duplicate outcome and does not execute the protected mutation again;
7. the implementation must not mark a delivery durably complete before its protected mutation commits;
8. the implementation must not silently open an independent second transaction for inbox completion;
9. external/non-transactional side effects are not made exactly-once by this local database primitive and require their own accepted idempotency boundary.

The exact transaction API must reuse the retained P01 database abstraction rather than inventing another transaction framework.

## Processing state and result law

The minimum durable semantics must distinguish at least:

- first eligible processing attempt;
- already-applied duplicate delivery;
- conflicting identity/content reuse;
- transaction/persistence failure;
- concurrency conflict where another transaction is processing or has just committed the same identity.

Exact names/storage representation are implementation details. However:

- duplicate must be an explicit deterministic outcome, not an exception that callers are encouraged to ignore;
- conflict must fail closed and must not be projected as a harmless duplicate;
- a failure before commit must leave the event eligible for a later legitimate retry/redelivery;
- a committed completion record must survive restart;
- no state may imply downstream/external exactly-once completion beyond the local accepted mutation boundary;
- no retry count, backoff time, terminal-failure classification or quarantine state is introduced here.

## Concurrency law

Concurrent delivery of the same canonical event to the same processing scope must not apply the protected mutation twice.

Acceptance must prove that:

- a database uniqueness/CAS/locking mechanism enforces one committed processing identity per accepted scope;
- two concurrent attempts cannot both commit the protected mutation;
- the losing/concurrent attempt receives a deterministic duplicate/concurrency outcome after authoritative state is resolved;
- one tenant/consumer scope cannot block or consume another legitimate scope for the same EventID;
- cancellation or transaction abort cannot leave a false durable completion marker;
- deadlock/serialization/database errors fail safely and remain eligible for later retry under P04.06 policy, rather than being silently converted into completion.

P04.05 defines the correctness primitive only; scheduling and retry policy remain P04.06.

## Checkpoint interaction law

P04.03 checkpoints and P04.05 inbox completion represent different facts:

- checkpoint = durable consumption progress;
- inbox completion = local duplicate-safe application evidence for one processing identity.

Therefore:

- inbox completion does not automatically advance a checkpoint;
- checkpoint advancement does not prove a protected mutation was applied exactly once;
- a crash after local protected mutation + inbox commit but before checkpoint advancement may cause redelivery; P04.05 must convert that redelivery into an already-applied outcome;
- a crash before the local transaction commits leaves no accepted inbox completion and the delivery may be processed again;
- neither primitive may be used as an authorization credential.

## Payload and evidence law

The inbox should persist the minimum evidence required to prove identity and safe duplicate handling. It must not create an uncontrolled second event archive.

A later implementation should prefer bounded evidence such as:

- canonical EventID;
- owner/consumer/tenant/route scope identity;
- canonical envelope/version/content fingerprint where needed for conflict detection;
- accepted completion timestamp/revision;
- bounded safe outcome metadata required for diagnostics.

Requirements:

- confidential/restricted payload content must not be copied into logs/errors/diagnostic metadata;
- secrets remain prohibited;
- if canonical content fingerprinting is used, the normalization/hash law must be deterministic and versioned enough to avoid false duplicate/conflict classification;
- inbox state must not become a substitute audit log for P01.11;
- retention/cleanup must not silently erase evidence needed to prevent duplicate protected mutation while duplicate delivery remains possible.

## Required tests / acceptance criteria

Before P04.05 promotion, the later authorized implementation must prove on its exact final head:

1. first delivery can atomically commit one synthetic protected local mutation plus one inbox completion record;
2. mutation failure leaves no durable inbox completion;
3. inbox persistence failure prevents the protected mutation from committing;
4. exact duplicate redelivery after commit returns already-applied and does not repeat the mutation;
5. restart followed by duplicate redelivery remains duplicate-safe;
6. crash/restart after protected mutation + inbox commit but before P04.03 checkpoint advancement does not repeat the protected mutation;
7. failure/rollback before commit permits a later legitimate processing attempt;
8. same EventID may be processed independently by different authorized consumer scopes without cross-consumer suppression;
9. tenant-scoped processing identity is isolated and caller-controlled scope rebinding fails closed;
10. same processing identity with conflicting canonical content/envelope evidence fails closed rather than being treated as duplicate;
11. two concurrent same-scope attempts cannot both commit the protected mutation;
12. cancellation/database/concurrency failure never creates a false completion record;
13. inbox completion and checkpoint advancement remain distinct facts;
14. no retry/backoff/DLQ/quarantine policy, schema registry, job runtime, broker/provider choice, business-feature authority or AI/model/agent authority appears in the diff;
15. no end-to-end exactly-once or global-ordering claim is introduced;
16. repository Go quality and all retained P01/P02/P03/P04.01-P04.04 regressions remain green under exact-head Omnexa Governance.

If a migration is authorized, acceptance additionally proves fresh install, upgrade/ledger integrity, owner isolation and rollback/forward-recovery evidence.
