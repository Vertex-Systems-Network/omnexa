# P01.04 — PostgreSQL Connection & Migration Foundation

- Phase: `P01`
- State: `active`
- Owner/domain: `kernel.data`
- Depends on: `P01.03 done`
- Blocks: `P01.05`–`P01.12`
- Change class: `B`

> **Implementation authorization:** `kernel_code_authorized=true` for this package only. `business_feature_code_authorized=false`. P01.04 is the sole active executable scope.

## Objective

Establish the governed PostgreSQL connectivity and migration substrate that later kernel capabilities/modules can consume without sharing ownership of each other's schemas or relying on hidden manual SQL.

## In scope

- PostgreSQL connection/pool construction from P01.02 configuration;
- bounded startup/connectivity behavior and safe provider error mapping through the completed P01.03 failure primitives;
- transaction helper boundary without domain writes;
- migration runner/version ledger foundation;
- deterministic fresh-install and upgrade execution;
- advisory/coordination strategy preventing conflicting migration execution where required;
- repository conventions for owner-scoped migrations;
- test database lifecycle using synthetic data only;
- completed P01.01-P01.03 regression preservation;
- GitHub-hosted PostgreSQL integration/migration evidence.

## Explicitly out of scope

P01.04 must not implement:

- tenant/organization tables (`P02`);
- module runtime migrations/ownership registry (`P03`);
- event outbox/inbox (`P04` phase);
- business schemas or seed data;
- cross-module SQL access;
- cache/storage abstractions (`P01.05`/`P01.06`);
- logging/OpenTelemetry (`P01.07`);
- health endpoints (`P01.08`);
- backups, HA topology or production database operations automation;
- ORM/domain repository layers for later business modules.

## Architecture & security invariants

PostgreSQL remains the OLTP source of truth. Every future schema/write model has one authoritative owner. Migrations are versioned, reviewable and reproducible; no startup path silently mutates unrelated owner schemas.

Database credentials are `RESTRICTED` and must never be logged, exposed through P01.03 public failures, committed to the repository or copied into build/test artifacts. Test execution uses synthetic data only. Connection/migration failures must fail closed and must not claim successful schema state.

The package may add the minimum justified PostgreSQL Go driver/migration dependencies needed for this foundation, but may not pull forward later infrastructure or business frameworks merely for convenience.

## Acceptance criteria

1. Fresh empty PostgreSQL database migrates deterministically from zero.
2. Re-running the migration set is safe and does not duplicate effects.
3. Upgrade path from at least one prior synthetic fixture version succeeds deterministically.
4. Failed migration reports a safe P01.03 structured failure and does not claim success.
5. Connection establishment/exhaustion/timeout behavior is bounded and testable.
6. Database configuration is consumed through P01.02 without secret disclosure.
7. Transaction helper behavior is explicit and does not introduce domain writes.
8. Migration ownership/layout prevents hidden cross-owner schema mutation.
9. No tenant/module/business tables, event fabric or later P01 capability is introduced.
10. P01.01-P01.03 regression verifiers remain PASS.
11. Applicable G0/G1/G2/G3/G4/G5/G7 evidence is PASS on GitHub-hosted `ubuntu-24.04` with a governed PostgreSQL test service.

## Required tests / evidence

Required:

- configuration-to-PostgreSQL connection construction tests with secrets redacted;
- successful connection/ping integration test;
- bounded invalid/unavailable connection negative test;
- transaction commit/rollback helper tests without domain models;
- fresh migration from empty database;
- idempotent second migration execution;
- deterministic upgrade from a prior synthetic fixture version;
- intentionally failing migration/rollback-state negative test;
- migration version-ledger assertions;
- owner/scope guard proving no P02/P03/business schema is created;
- P01.01/P01.02/P01.03 regression verification;
- build/package evidence.

No production credentials, production data or manually prepared hidden SQL state may be used as test evidence.
