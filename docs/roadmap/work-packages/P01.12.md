# P01.12 — Developer CLI Baseline

- Phase: `P01`
- State: `planned`
- Owner/domain: `kernel.developer`
- Depends on: `P01.11 done`
- Blocks: `P01 exit`
- Change class: `B`

> Specification-only while `kernel_code_authorized=false`.

## Objective

Deliver the first repository-owned Omnexa developer CLI/command surface that composes P01 foundations into deterministic local/CI workflows without hiding required steps or granting privileged runtime authority.

## In scope

- stable `omnexa`/repository command surface for version, verify, build/test helpers and approved local diagnostics;
- canonical `verify` orchestration mapping to applicable quality gates;
- explicit exit codes and structured-safe output;
- command help/version metadata;
- configuration integration from P01.02;
- migration command boundary from P01.04 where explicitly safe;
- diagnostic/health command boundary from P01.08;
- no-secret output policy;
- deterministic invocation from clean checkout and CI.

## Out of scope

- production super-admin CLI;
- tenant/user/role administration (`P02`);
- module install/runtime CLI (`P03`);
- event/workflow/domain commands (`P04+`);
- deployment/Kubernetes orchestration;
- interactive commands that bypass auditable APIs.

## Security invariants

CLI convenience never creates authority. Privileged future operations must authenticate/authorize through governed capabilities and audit paths. Command output must redact secrets and RESTRICTED data. Destructive commands require explicit semantics; no hidden SQL/file mutation is permitted.

## Acceptance criteria

1. Clean checkout exposes deterministic help/version/verify behavior.
2. `verify` returns non-zero when any required applicable gate fails.
3. CLI output contains no secret/local credential leakage.
4. Commands compose existing P01 capabilities rather than reimplementing them.
5. CI can invoke the same semantic verification command family used locally.
6. No P02/P03/business/deployment administration is introduced.
7. Applicable G0–G8 evidence for the P01 exit risk profile is recorded accurately.
8. P01 fresh-install exit gate proves start, migrate, health-check, telemetry and tests reproducibly without hidden manual steps.

## Completion evidence / P01 exit evidence

Before P01 can become `done`, record exact evidence that a clean environment can:

- resolve configuration;
- build/start the kernel;
- migrate a fresh PostgreSQL database;
- exercise cache/storage provider contract tests;
- emit safe logs/telemetry;
- report readiness/diagnostics;
- execute job/config-registry/audit primitives tests;
- run the canonical developer verification command;
- complete required security/supply-chain/build gates.

## State transition

`planned -> active` only after P01.11 `done`; `active -> verification -> done` only when the P01 phase exit gate passes. P02 may not activate before P01 is reconciled `done` with evidence.
