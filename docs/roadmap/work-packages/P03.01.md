## Objective

Define and implement the canonical machine-readable module manifest schema that turns `MODULE_STANDARD.md` semantics into deterministic validated runtime metadata without executing package code.

## In scope

- stable module ID, human name, module version, contract version, maturity status, owner and runtime metadata;
- required platform version and required/optional/platform dependency declarations;
- declared provided/consumed capabilities, permissions, events, workflow hooks, UI slots, settings, feature flags, data classifications, migrations, lifecycle hooks and health checks;
- minimal optional forward-compatible metadata hooks for publisher/provenance/SBOM/declared data-network-secret scope needed by P03 contract alignment, without trust enforcement;
- schema/version compatibility rules, bounded parsing and deterministic validation errors;
- positive/negative fixtures for valid, malformed, conflicting and boundary manifests.

## Out of scope

- module registry/discovery;
- dependency graph resolution;
- lifecycle execution or persistence;
- marketplace/package download/signature verification/sandboxing;
- P04 events/workflows, business modules or AI/model/agent runtime.

## Security and architecture invariants

- manifest/package metadata is untrusted input;
- parsing/validation must not execute module hooks or arbitrary code;
- manifests contain declarations and secret references only, never secret values/credentials;
- IDs/versions/owners are stable and machine-validatable;
- schema evolution is versioned; unknown future fields cannot silently change authority;
- declared permissions/capabilities are metadata, not authorization grants;
- existing P02 tenant/authorization/audit invariants remain unchanged.

## Acceptance criteria

1. valid reference manifests representing mandatory `MODULE_STANDARD.md` semantics parse and validate deterministically.
2. missing/invalid identity, version, owner, dependency, contribution and security declaration fields fail with stable safe errors.
3. malformed/oversized/unsupported-version metadata is bounded and cannot cause code execution or secret exposure.
4. required/optional/platform dependency classes are represented distinctly; forbidden/private coupling is not representable as an implicit valid dependency.
5. stable IDs/version fields are suitable for later registry, graph, trust, federation and performance attribution without implementing those systems.
6. tests cover compatibility/version, duplicate declaration, invalid identifier and sensitive-value negative cases.
7. repository Go quality and all P01/P02 regressions pass on canonical GitHub-hosted `ubuntu-24.04`.
