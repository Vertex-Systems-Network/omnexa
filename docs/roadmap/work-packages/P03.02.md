# P03.02 — Registry & Deterministic Discovery

- Phase: `P03`
- State: `planned`
- Owner/domain: `kernel.modules`
- Depends on: `P03.01`
- Blocks: `P03.03`
- Change class: `B`

> Readiness only. `business_feature_code_authorized=false`; implementation requires P03.02 to become the sole active package.

## Objective

Build a deterministic registry/discovery layer over validated P03.01 manifests so available module identities and versions can be enumerated without implicit hook execution, network trust assumptions or hidden filesystem coupling.

## In scope

- registry records for validated module identity/version/owner/source metadata;
- deterministic discovery from explicitly approved repository/runtime sources;
- duplicate/conflicting module ID/version rejection;
- stable lookup/list ordering and source/version identity;
- separation between discovered/available metadata and installed/enabled lifecycle state;
- discovery diagnostics safe for operators and later health integration.

## Out of scope

- remote marketplace/catalog download;
- dependency ordering/compatibility resolution;
- install/enable/disable execution;
- signature/trust decisions;
- federated products, business modules or AI runtime.

## Security and architecture invariants

- discovery parses validated metadata and must not execute module code;
- discovery sources are explicit; arbitrary path/network scanning is forbidden;
- duplicate identity cannot be resolved by nondeterministic last-write-wins behavior;
- registry metadata cannot grant permissions/capability authority;
- package paths/source details exposed in diagnostics must respect classification/redaction.

## Acceptance criteria

1. deterministic discovery returns the same validated registry from the same source set regardless of enumeration order.
2. duplicate/conflicting IDs or versions fail closed with explicit diagnostics.
3. malformed/unvalidated manifests never enter the registry.
4. discovery performs no lifecycle hook execution or unapproved network access.
5. discovered versus installed/enabled state is structurally distinguishable.
6. tests cover empty source, duplicate, conflicting version, malformed source and deterministic-order cases.
7. repository Go quality and P01/P02 regressions pass on GitHub-hosted `ubuntu-24.04`.
