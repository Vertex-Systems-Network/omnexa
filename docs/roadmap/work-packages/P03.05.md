## Objective

Bind module-declared settings and feature flags to the existing governed configuration foundation so module lifecycle and availability can consume typed configuration without creating a second settings system or hidden authorization path.

## Implemented scope

- registration of manifest-declared setting/feature-flag definitions;
- stable owner/module keys, types, validation, defaults and explicit scope;
- lifecycle-aware availability/read semantics;
- tenant/org scoping only through trusted existing configuration context;
- safe unregister/disable behavior that preserves required historical configuration;
- collision/ownership validation.

## Accepted P03.05 binding design

P03.05 does **not** change manifest schema v1 or v2. Existing `settings` and `feature_flags` entries remain declaration identifiers and each entry is interpreted as the exact fully-qualified `kernel.configuration.Key` that the module claims.

Trusted kernel/module registration supplies a `ModuleConfigurationRegistration` containing the existing typed `kernel.configuration.Definition`, an explicit `global|scoped` registration scope, and — only for scoped entries — an existing P02.09 `kernel.configuration.SettingPolicy`.

The accepted binder verifies before constructing the configuration registry:

- every manifest-declared setting/flag has exactly one registration;
- every supplied typed definition is declared by exactly one discovered module;
- `Definition.Key` exactly equals the manifest declaration string; no implicit prefixing, aliasing or encoded mini-language is permitted;
- `Definition.Owner` exactly equals the discovered module ID;
- entries under `settings` bind only to `ClassRuntimeConfig`;
- entries under `feature_flags` bind only to `ClassFeatureFlag`;
- registration scope is explicit rather than inferred;
- `global` registrations reject scoped policy;
- `scoped` registrations require exactly one key-matching P02.09 `SettingPolicy` that passes existing `kernel.configuration` policy validation;
- existing `kernel.configuration.NewRegistry` remains the validation/duplicate/type/default authority and no second settings registry is created.

The package-private validated manifest snapshot retains accepted setting/flag declaration identifiers so P03.05 consumes the same validated discovery snapshot that created module identity. Raw manifests are not reparsed independently to create configuration authority.

Lifecycle semantics remain non-destructive. Configuration definitions remain historically available for safe installed/disabled/suspended/archived/detached/recovery-required history, while only an enabled module is runtime-active. Never-installed (`available`) and purged modules are unavailable through module binding. Lifecycle state grants no configuration authority, permission or tenant scope.

For scoped registrations, binding exposes validated P02.09 `SettingPolicy` copies only so callers can construct the existing `kernel.configuration.ScopedService`. Trusted tenant/organization scope remains exclusively behind `ScopeFromTenantContext` / `ScopeFromOrganizationContext`; P03.05 accepts no raw tenant/org identifiers and introduces no alternate scoped read/write path.

## Security and architecture invariants

- `kernel.configuration` remains authoritative for setting/flag state;
- settings and flags cannot create authority, bypass policy or select untrusted tenant scope;
- secret values are not exposed through generic module metadata/health;
- disabling a module does not silently destroy configuration required for safe re-enable/history;
- registration collisions fail closed;
- invalid/missing/ambiguous scoped policy fails closed before runtime registration;
- P03.04 lifecycle state remains an availability/precondition input only and does not become a second configuration owner.
