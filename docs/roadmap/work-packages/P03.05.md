# P03.05 — Module Settings & Feature Flags

- Phase: `P03`
- State: `active`
- Owner/domain: `kernel.modules` with `kernel.configuration` integration
- Depends on: `P03.04`
- Blocks: `P03.06`
- Change class: `B`

> P03.05 becomes the sole active package only after the governed P03.04 completion/P03.05 activation closure PR passes exact-final-head canonical governance and merges to protected `main`. `kernel.configuration` remains authoritative for setting/flag values; `business_feature_code_authorized=false` remains unchanged. P03.06+ stays planned/locked.

## Objective

Bind module-declared settings and feature flags to the existing governed configuration foundation so module lifecycle and availability can consume typed configuration without creating a second settings system or hidden authorization path.

## In scope

- registration of manifest-declared setting/feature-flag definitions;
- stable owner/module keys, types, validation and defaults;
- lifecycle-aware availability/read semantics;
- tenant/org scoping only through trusted existing configuration context;
- safe unregister/disable behavior that preserves required historical configuration;
- collision/ownership validation.

## Out of scope

- business-feature configuration domains;
- entitlements/licensing product logic;
- flags that grant permissions;
- environment ALM/config-as-code (`XALM-200`);
- P03.06+ implementation;
- P04+ runtime;
- strategic X-program runtime;
- AI/model/agent runtime.

## Security and architecture invariants

- `kernel.configuration` remains authoritative for setting/flag state;
- settings and flags cannot create authority, bypass policy or select untrusted tenant scope;
- secret values are not exposed through generic module metadata/health;
- disabling a module does not silently destroy configuration required for safe re-enable/history;
- registration collisions fail closed;
- P03.04 lifecycle state remains an availability/precondition input only and does not become a second configuration owner.

## Acceptance criteria

1. valid module setting/flag declarations register deterministically through existing configuration contracts.
2. invalid type/scope/duplicate/owner definitions are rejected.
3. tenant-scoped reads/writes use trusted P02 context and cross-tenant negative tests pass where applicable.
4. feature flags cannot grant permissions or bypass `kernel.authorization`.
5. disable/re-enable preserves required configuration semantics without manual repair.
6. no duplicate configuration subsystem is introduced.
7. Go quality and all retained P01/P02/P03.01/P03.02/P03.03/P03.04 regressions pass on GitHub-hosted `ubuntu-24.04`.
8. no P03.06+ implementation is added.

## Completion evidence

None while active. Future completion requires a separate P03.05 implementation PR from the exact protected-main SHA established after this activation closure merges, a dedicated P03.05 verifier, retained regressions, and a later governed closure/state transition.

## State transition

`planned -> active -> verification -> done`; P03.05 is the sole active package after this transition merges. P03.06 remains planned and unauthorized until P03.05 separately passes exact-head acceptance, merges, and a later governed closure activates P03.06. Do not auto-advance.
