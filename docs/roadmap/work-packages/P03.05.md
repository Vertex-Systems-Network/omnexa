# P03.05 — Module Settings & Feature Flags

- Phase: `P03`
- State: `active`
- Owner/domain: `kernel.modules` with `kernel.configuration` integration
- Depends on: `P03.04`
- Blocks: `P03.06`
- Change class: `B`

> P03.05 becomes the sole active package only after the governed P03.04 completion/P03.05 activation closure PR passes exact-final-head canonical governance and merges to protected `main`. `kernel.configuration` remains authoritative for setting/flag values; `business_feature_code_authorized=false` remains unchanged. P03.06+ stays planned/locked.

## Objective

Bind module-declared settings and feature flags to the existing governed configuration foundation so module lifecycle and availability can consume typed configuration without creating a second settings system or hidden authorization path.

## In scope

- registration of manifest-declared setting/feature-flag definitions;
- stable owner/module keys, types, validation, defaults and explicit scope;
- lifecycle-aware availability/read semantics;
- tenant/org scoping only through trusted existing configuration context;
- safe unregister/disable behavior that preserves required historical configuration;
- collision/ownership validation.

## P03.05 binding design decision

P03.05 does **not** change manifest schema v1 or v2. Existing `settings` and `feature_flags` entries remain declaration identifiers and, for P03.05 binding, each entry is interpreted as the exact fully-qualified `kernel.configuration.Key` that the module claims.

Trusted kernel/module registration supplies a `ModuleConfigurationRegistration` containing the existing typed `kernel.configuration.Definition`, an explicit `global|scoped` registration scope, and — only for scoped entries — an existing P02.09 `kernel.configuration.SettingPolicy`.

The binder must verify all of the following before constructing the configuration registry:

- every manifest-declared setting/flag has exactly one registration;
- every supplied typed definition is declared by exactly one discovered module;
- `Definition.Key` exactly equals the manifest declaration string; no implicit prefixing, aliasing or encoded mini-language is permitted;
- `Definition.Owner` exactly equals the discovered module ID, preventing one module from claiming another module's key;
- entries under `settings` bind only to `ClassRuntimeConfig`;
- entries under `feature_flags` bind only to `ClassFeatureFlag`; operational kill switches remain a separate governed configuration concern;
- registration scope is explicit rather than inferred;
- `global` registrations MUST NOT carry a scoped policy;
- `scoped` registrations MUST carry exactly one key-matching P02.09 `SettingPolicy` and that policy must pass the existing `kernel.configuration` policy validator;
- existing `kernel.configuration.NewRegistry` remains the validation/duplicate/type/default authority and no second settings registry is created.

The package-private validated manifest snapshot retains the accepted setting/flag declaration identifiers so P03.05 consumes the same validated discovery snapshot that created module identity. Raw manifests must not be reparsed independently to create configuration authority.

Lifecycle semantics are non-destructive. A configuration definition remains historically readable for installed/disabled/suspended/archived/detached/recovery-required module states, while only an enabled module is runtime-active. Never-installed (`available`) and purged modules are unavailable through the module binding. Lifecycle state cannot create configuration authority, permissions or tenant scope.

For scoped registrations, the binding exposes validated P02.09 `SettingPolicy` copies only so callers can construct the existing `kernel.configuration.ScopedService`. Trusted tenant/organization scope still comes exclusively from `ScopeFromTenantContext` / `ScopeFromOrganizationContext`; the P03.05 binder accepts no raw tenant/org identifiers and introduces no alternate scoped read/write path. Global registrations remain on the existing P01.10 global evaluator contract and carry no P02.09 scope policy.

## Out of scope

- business-feature configuration domains;
- entitlements/licensing product logic;
- flags that grant permissions;
- environment ALM/config-as-code (`XALM-200`);
- P03.06+ implementation;
- P04+ runtime;
- strategic X-program runtime;
- AI/model/agent runtime.

## Security and architecture invariants

- `kernel.configuration` remains authoritative for setting/flag state;
- settings and flags cannot create authority, bypass policy or select untrusted tenant scope;
- secret values are not exposed through generic module metadata/health;
- disabling a module does not silently destroy configuration required for safe re-enable/history;
- registration collisions fail closed;
- invalid/missing/ambiguous scoped policy fails closed before runtime registration;
- P03.04 lifecycle state remains an availability/precondition input only and does not become a second configuration owner.

## Acceptance criteria

1. valid module setting/flag declarations register deterministically through existing configuration contracts.
2. invalid type/scope/duplicate/owner definitions are rejected.
3. tenant-scoped reads/writes use trusted P02 context and cross-tenant negative tests pass where applicable.
4. feature flags cannot grant permissions or bypass `kernel.authorization`.
5. disable/re-enable preserves required configuration semantics without manual repair.
6. no duplicate configuration subsystem is introduced.
7. Go quality and all retained P01/P02/P03.01/P03.02/P03.03/P03.04 regressions pass on GitHub-hosted `ubuntu-24.04`.
8. no P03.06+ implementation is added.
