# P04.04 — Transactional Outbox Reliability Primitive

- Phase: `P04`
- State: `prepared / planned / locked`
- Owner/domain: `kernel.events`
- Depends on: accepted `P04.01`, accepted P04.03 implementation/completion evidence, and a later separate governed P04.03 closure/P04.04 activation transaction
- Blocks: `P04.05`
- Change class: `B`

> This document prepares the P04.04 contract only. It is **not implementation authority**. P04.04 runtime, schema, migration or state work must not begin until a separate governance/state/continuity transaction records P04.03 done, explicitly accepts this contract, makes P04.04 the sole active package, passes exact-head Omnexa Governance, merges through the protected path, and protected `main` is re-read.

## Objective

Define the minimum provider-neutral transactional outbox reliability boundary that can atomically retain one canonical P04.01 event with an authorized local PostgreSQL state mutation and later relay that committed event through the accepted P04.02 publication boundary without selecting a broker, claiming end-to-end exactly-once behavior, implementing consumer inbox/deduplication, or pulling retry/DLQ policy forward from later packages.

P04.04 closes the producer-side database-to-event crash window only. It does **not** prove that a downstream consumer applied a protected business mutation exactly once. Duplicate relay remains possible, especially after publish success but before the durable outbox record is marked published; the accepted P04.03 duplicate/replay laws therefore remain authoritative.

## Retained authority and architecture

P04.04 must compose existing accepted foundations rather than create parallel ones:

- canonical event identity and payload remain the accepted P04.01 `events.Envelope` contract;
- route/publication ownership remains the accepted P04.02 producer/registration boundary;
- duplicate/restart/no-global-ordering semantics remain compatible with P04.03;
- local PostgreSQL transaction behavior must remain compatible with the retained P01 `database.InTransaction` boundary instead of inventing a second transaction framework;
- SQL migration execution/ledger/advisory-lock authority remains the retained P01 migration runner;
- migration ownership declarations remain compatible with P03.09; P04.04 must not create another migration executor or ownership registry;
- P01.11 audit transport remains a separate append-only audit concern and must not be represented as transactional outbox durability.

No event, outbox row, relay state, checkpoint, offset, consumer identity or transport receipt grants authorization or cross-module write authority.

## Required transactional law

A later authorized implementation must prove the following producer-side atomicity boundary:

1. when an authorized state mutation and event creation must be atomic, the canonical event outbox enqueue participates in the **same local PostgreSQL transaction** as that state mutation;
2. the atomic path must not silently open an independent second transaction for the outbox write;
3. if the state mutation fails or the enclosing transaction rolls back, the corresponding outbox row is not committed;
4. if the outbox enqueue fails, the enclosing state-mutation transaction fails rather than committing state without its required event;
5. successful transaction commit makes the owner mutation and outbox event record durable together from the perspective of that local database transaction;
6. the relay observes only committed outbox records and cannot publish an uncommitted event;
7. P04.04 does not make an external broker publish and the PostgreSQL commit one distributed transaction.

The transaction boundary is producer-side reliability only. Consumer-side protected mutation, inbox/deduplication and idempotency persistence remain P04.05 or later work.

## Canonical outbox identity and record law

An outbox record must retain the canonical event identity rather than create a provider-specific or relay-specific event contract.

At minimum the persistence boundary must preserve enough information to reconstruct or relay the accepted canonical P04.01 envelope unchanged, including:

- stable `EventID`;
- producer/source identity;
- event type and event/schema version identity;
- occurred time;
- trusted tenant context where present;
- organization context where present;
- correlation and causation identities;
- data classification;
- canonical validated event payload and remaining accepted envelope metadata required for faithful relay.

Requirements:

- a relay attempt must not mint a replacement event ID for an already committed outbox event;
- provider/broker offsets, topics, acknowledgements or SDK types must not become canonical event identity;
- outbox persistence must not weaken P04.01 payload bounds, validation, classification or secret-handling rules;
- log/error/diagnostic surfaces must not expose confidential/restricted payload content, credentials, connection strings or provider topology;
- outbox row identity and event identity are not authorization credentials.

If the implementation permits repeated enqueue attempts for the same canonical `EventID`, an exact same-event retry may be treated deterministically as unchanged, while the same `EventID` with conflicting canonical content must fail closed. This is producer-side identity integrity only; it is **not** P04.05 consumer deduplication.

## Outbox state model

The minimum producer-side state model must make committed publication progress explicit without importing P04.06 retry policy.

Conceptually, an outbox record is one of:

- committed and pending publication;
- committed and recorded as published.

The exact names/storage representation are implementation details, but the following laws are required:

- pending committed records remain discoverable after process restart;
- a record is not marked published before the accepted P04.02 publication call succeeds;
- a publication failure leaves the record pending/recoverable;
- a crash/restart before publication leaves the record pending/recoverable;
- a crash after successful publication but before the published mark can cause the same canonical event to be relayed again;
- therefore duplicate publication remains explicitly possible and must be tested;
- a published mark means only that the producer-side relay recorded a successful publication attempt; it does not mean a downstream protected mutation happened exactly once;
- malformed or contradictory stored state must fail closed and must not be silently reset to pending/published according to a permissive default;
- records must not be silently deleted merely because publication was attempted.

P04.04 must not define retry backoff schedules, maximum attempts, terminal failure classification, DLQ/quarantine policy or poison-event handling. Those belong to P04.06.

## Relay boundary

The P04.04 relay is a provider-neutral producer-side reliability primitive.

A later implementation must prove:

- relay input is committed pending outbox state only;
- publication uses the accepted P04.02 publication abstraction/ownership boundary rather than selecting Kafka, NATS, RabbitMQ, Redis Streams or another provider;
- the relay preserves the canonical P04.01 envelope unchanged;
- publication failure leaves work recoverable for a later explicit relay attempt;
- duplicate publication around crash/restart is expected rather than hidden;
- concurrent relay attempts cannot corrupt publication state, permanently skip committed pending work, or mark a record published without a successful publication result;
- one record's state cannot be rebound to another owner, event, tenant or canonical identity;
- no global event ordering guarantee is introduced by outbox row order, database sequence, timestamp or relay scheduling.

P04.04 may establish the minimum safe claim/compare-and-set/lease semantics required to prevent state corruption, but it must not pull P04.06 scheduling/backoff policy or P04.08 background-job ownership/execution into this package.

## Crash/restart acceptance law

At minimum, P04.04 must preserve these explicit crash windows:

### Crash before transaction commit

- owner mutation and outbox event both remain uncommitted/rolled back;
- no relay-visible event may exist from that failed atomic operation.

### Commit succeeds, process crashes before relay

- the committed pending outbox event remains discoverable on restart;
- restart/recovery does not require reconstructing the event from mutable business state.

### Publish fails

- the event remains pending/recoverable;
- no false published mark is written.

### Publish succeeds, process crashes before published mark

- the event may be published again after restart;
- duplicate relay is therefore part of the accepted model;
- no exactly-once claim may be made.

### Published mark succeeds

- the producer-side record has accepted publication progress;
- this does not certify consumer receipt, consumer checkpoint advancement, inbox deduplication or protected business mutation.

## Reconciliation, retention and cleanup boundary

P04 readiness requires recoverability without conflating later operator tooling.

P04.04 must therefore establish that:

- committed pending records are enumerable/recoverable enough for bounded relay/reconciliation proof;
- malformed or stranded state is surfaced safely rather than silently discarded;
- implementation rollback/forward-recovery cannot erase accepted canonical event identity required for investigation;
- publication records are not automatically deleted solely to keep the table small;
- any later retention/cleanup mechanism must preserve required audit/evidence obligations and cannot delete independent P01.11 audit records;
- broad operator recovery UX, replay consoles and reliability dashboards remain P04.09;
- poison-event quarantine remains P04.06.

This package need not define final production retention duration or a cleanup scheduler unless a later activation explicitly extends the accepted P04.04 budget with evidence. Default behavior should favor preserved/recoverable state over silent deletion.

## Tenant, owner and security invariants

- outbox persistence is owned by the accepted authoritative owner and must not create cross-module private-table write authority;
- tenant-scoped canonical events retain their trusted tenant identity unchanged;
- one tenant/owner/event scope cannot read, claim, mark or overwrite another scope's outbox state through caller-controlled namespace values;
- outbox/event identities do not grant RBAC/capability authority;
- authorization still occurs at the actual protected action boundary under accepted P02/P03 rules;
- confidential/restricted event payloads may only be persisted as the already-authorized canonical event content and must not be copied into logs, failure messages, health snapshots or diagnostic metadata;
- secret values remain prohibited from event payloads and diagnostics;
- database/provider failure details are mapped through existing safe failure conventions;
- cancellation/context propagation must follow repository Go conventions without silently converting cancelled work into published state.

## Persistence and migration decision gate

This **preparation carrier adds no migration** and authorizes no schema change.

A later P04.04 activation/implementation plan must re-read fresh protected main and explicitly decide whether PostgreSQL outbox persistence is required. If it is required, the plan must record an exact migration/path/data budget before source mutation and prove:

- canonical migration owner and path under `kernel/migrations/<owner>/<version>_<name>.sql`;
- compatibility/change class and immutable migration identity;
- fresh-install and upgrade behavior through the retained P01 migration runner;
- rollback/forward-recovery behavior;
- owner and tenant isolation;
- no cross-owner SQL;
- no separate migration engine;
- no business-table schema mutation smuggled into `kernel.events` ownership;
- no P04.05/P04.06 schema semantics pulled forward.

The current expected owner is `kernel.events`, but the exact migration directory/version/name must be verified against the repository at activation/implementation time rather than hard-coded by this preparation document.

## Required tests / acceptance criteria

Before P04.04 promotion, the later authorized implementation must prove on its exact final candidate head:

1. an authorized synthetic/local owner mutation and required outbox enqueue commit together in the same PostgreSQL transaction;
2. owner mutation/callback failure rolls back the corresponding outbox event;
3. outbox enqueue failure prevents the required owner mutation from committing;
4. relay cannot observe or publish an uncommitted outbox row;
5. a producer restart with a committed pending row can recover and relay the same canonical event without reconstructing it from mutable business state;
6. publication failure leaves the event pending and does not create a false published mark;
7. successful publication followed by simulated mark failure/crash permits duplicate relay after restart and is documented/tested as at-least-once-compatible behavior;
8. successful published-state advancement is deterministic and does not claim consumer/business exactly-once completion;
9. canonical P04.01 event identity, tenant/correlation/causation/schema/classification metadata and payload remain unchanged across enqueue/relay;
10. conflicting reuse of one event/outbox identity fails closed without corrupting accepted state;
11. owner/tenant isolation prevents cross-scope read/claim/mark corruption;
12. concurrent relay attempts cannot permanently skip pending work or record an invalid published state;
13. malformed persisted state and database failures fail safely without leaking payloads, credentials or topology;
14. no broker/provider selection, P04.05 inbox/dedup, P04.06 retry/backoff/DLQ, P04.07 schema-registry runtime, P04.08 job-runtime ownership, business-handler or AI/model/agent authority appears in the diff;
15. no global-ordering or end-to-end exactly-once claim appears in behavior/docs;
16. repository Go quality plus all retained P01/P02/P03/P04.01/P04.02/P04.03 regressions remain green under exact-head Omnexa Governance.

If a migration is authorized, acceptance must additionally prove fresh install, upgrade/ledger integrity, owner isolation and rollback/forward-recovery evidence on the exact candidate head.

## Negative requirements

P04.04 MUST NOT:

- mark P04.03 done or activate itself from this preparation carrier;
- implement or activate P04.05+;
- implement consumer inbox/deduplication or protected-consumer idempotency persistence (`P04.05`);
- implement retry schedules/backoff, retry caps, terminal failure or DLQ/quarantine (`P04.06`);
- implement schema-registry/evolution runtime (`P04.07`);
- change background-job ownership/execution (`P04.08`);
- select Kafka, NATS, RabbitMQ, Redis Streams or another broker/provider;
- create a distributed transaction between PostgreSQL and a broker;
- claim exactly-once event delivery or exactly-once protected business mutation;
- infer global ordering from database IDs/timestamps/relay order;
- add business-domain handlers or cross-module private-table writes;
- treat P01.11 audit transport as transactional outbox persistence;
- create a second migration runner/ledger/ownership authority;
- grant business-feature or AI/model/agent runtime authority.

## Data / migration / rollback

- this preparation carrier: database migration `none`, persisted business-data mutation `none`, provider/spend `none`;
- later P04.04 persistence must not be inferred as automatically authorized solely because the package becomes active;
- implementation rollback must preserve already accepted P04.01-P04.03 contracts/evidence and must not rewrite historical completion receipts;
- committed outbox rows created by an accepted implementation must have an explicit forward-recovery/compatibility strategy rather than relying on destructive rollback of already-observed events;
- if schema rollback would risk losing an event that may already have been published, forward recovery is preferred over destructive deletion.

## Definition of Done

P04.04 is done only when:

- P04.03 accepted implementation evidence is already on protected main;
- this P04.04 contract has first been accepted through its own preparation governance path;
- a later separate P04.03 closure/P04.04 activation transaction makes P04.04 the sole authorized package;
- any required PostgreSQL persistence/migration is explicitly authorized and owner-bounded;
- implementation proves producer-state/outbox atomicity, restart recovery, duplicate-relay crash windows and safe publication-state advancement;
- exact-head canonical Governance passes;
- review provenance is recorded honestly;
- promotion merges through the governed integration path;
- P04.04 completion evidence is separately recorded;
- a later separate transition decides whether P04.05 may activate.

`P04.05+`, business-feature code, and AI/model/agent runtime remain locked until their later governed transactions.
