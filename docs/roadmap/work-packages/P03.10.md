## Objective

Expose classification-safe module health/state diagnostics covering lifecycle, dependencies, migration and capability availability while reusing the P01 health/readiness foundation and preserving failure isolation.

## In scope — authorized after activation merge

- stable module ID/version/state health identity;
- required versus optional dependency health/degradation;
- migration compatibility/pending/failure status needed for safe operation;
- capability/permission/UI registration availability summaries where applicable;
- explicit healthy/degraded/unavailable/failed diagnostics and bounded reason categories;
- deterministic reference-module health fixtures;
- focused positive/adversarial tests and a dedicated P03.10 verifier;
- canonical governance wiring after retained P03.09 verification.

## Out of scope

- System Graph storage/collector runtime;
- performance-budget analytics;
- business KPI monitoring;
- secrets/debug dumps or unrestricted topology disclosure;
- lifecycle command/control authority;
- authorization or permission-grant authority;
- P03.11 runtime;
- P04+ runtime;
- business-feature code;
- strategic X-program runtime;
- AI/model/agent runtime.

## Security and architecture invariants

- health is diagnostic evidence, not authorization or lifecycle command authority;
- required dependency failure is explicit/fail-closed; optional absence is selectively degraded;
- migration inconsistency cannot be presented as healthy;
- health output never includes credentials, secret values, raw tenant/org authority, internal stack traces or unnecessary RESTRICTED data;
- module failure cannot make unrelated health endpoints incorrect/unavailable where isolation is feasible;
- stable identity/version fields remain suitable for later XSG/XPF/XPERF correlation without implementing those systems;
- P01 health/readiness/observability remains the retained platform foundation rather than being replaced;
- P03.09 migration ownership metadata remains authoritative for migration compatibility/ownership interpretation;
- P03.07 authorization and P03.08 UI metadata remain non-granting inputs only;
- no hidden generic RPC/service-mesh, topology-collector or business-feature shortcut is introduced.

## Acceptance criteria

1. health accurately reflects module lifecycle state and required/optional dependency status.
2. required missing dependency reports unavailable/failure; optional missing dependency reports selective degradation.
3. migration ownership/compatibility/pending/failure inconsistency cannot be reported healthy.
4. capability/permission/UI availability summaries remain diagnostic only and cannot grant authority.
5. diagnostics remain classification-safe and do not expose secrets, raw tenant/org authority or internal stack traces.
6. unrelated healthy modules remain accurately reportable when one reference module fails.
7. tests cover healthy, degraded, required-dependency failure, migration mismatch and lifecycle state changes.
8. retained P01/P02/P03.01-P03.09 regressions pass on GitHub-hosted `ubuntu-24.04`.
9. a dedicated P03.10 verifier pins classification-safe diagnostics, fail-closed required dependencies, selective degradation, migration inconsistency and failure isolation.
10. no P03.11+, P04+ or business-feature runtime is introduced.
