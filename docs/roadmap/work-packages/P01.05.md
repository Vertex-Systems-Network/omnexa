# P01.05 — Cache Abstraction

- Phase: `P01`
- State: `active`
- Owner/domain: `kernel.cache`
- Depends on: `P01.04 done`
- Blocks: `P01.06`–`P01.12`
- Change class: `B`

> **Implementation authorization:** `kernel_code_authorized=true` for P01.05 only. `business_feature_code_authorized=false`. P01.05 is now the sole active executable kernel scope.

## Objective

Provide a small Redis-compatible cache/coordination boundary with explicit keys, expiry, serialization and failure behavior so caching can improve performance without becoming a hidden source of authority or correctness.

## In scope

- cache interface and Redis-compatible provider adapter;
- namespaced/versioned key conventions;
- explicit TTL semantics;
- typed serialization boundary;
- get/set/delete and bounded atomic primitives required by the kernel;
- connection/config integration through P01.02;
- provider failures mapped through the completed P01.03 structured failure contract;
- cache-miss versus provider-failure distinction;
- deterministic local/test fake only where semantics match the contract;
- synthetic Redis-compatible integration evidence on the GitHub-hosted governance lane;
- P01.01-P01.04 regression preservation.

## Explicitly out of scope

P01.05 must not implement:

- business-domain cache keys or cached business models;
- sessions/authentication/identity semantics (`P02`);
- tenant/organization implementation (`P02`);
- module-runtime registry/state (`P03`);
- distributed job/event fabric (`P04` phase);
- object/file storage (`P01.06`);
- logging/OpenTelemetry (`P01.07`);
- health/readiness endpoints (`P01.08`);
- job/scheduler primitives (`P01.09`);
- feature-flag/configuration registry (`P01.10`);
- audit transport (`P01.11`);
- generic distributed locks unless a concrete P01.05 invariant requires a narrowly bounded coordination primitive;
- using cache as system of record.

## Architecture & security invariants

Cache loss, flush, eviction or provider restart must not corrupt authoritative state. PostgreSQL remains authoritative where persistent state exists.

Future tenant-sensitive keys must include authoritative scope before use, but P01.05 does not implement tenancy. `RESTRICTED` secrets/auth equivalents are prohibited as ordinary cached payloads unless a later approved security contract explicitly permits them. Provider outage must degrade/fail according to caller policy, never bypass authorization or convert cache content into authority.

Cache configuration credentials are sensitive and must never appear in public P01.03 failures, logs or test artifacts. Tests use synthetic data only.

## Acceptance criteria

1. Key namespace/version behavior is deterministic and prevents accidental unscoped collisions.
2. TTL/expiry semantics are explicit, bounded and testable.
3. Cache miss and provider error are distinguishable through stable kernel behavior.
4. Serialization incompatibility/corruption fails safely without returning ambiguous trusted data.
5. Provider restart/flush/eviction cannot violate P01 correctness or create an authoritative state dependency.
6. Connection/acquisition/operation timeout and cancellation behavior are bounded.
7. Get/set/delete behavior is covered against a governed Redis-compatible test service.
8. Any atomic primitive included in scope has deterministic contract/integration evidence.
9. Sensitive provider configuration is redacted from public failures/artifacts.
10. No business/session/tenant/module/event/storage/telemetry/later-P01 semantics are implemented.
11. P01.01-P01.04 regression verifiers remain PASS.
12. Applicable G0/G1/G2/G3/G5/G6/G7 evidence is PASS on GitHub-hosted `ubuntu-24.04`.
