# Omnexa Future Domain Expansion Backlog

Status: **Strategic candidates — not implementation authority**

## 1. Purpose

P00-P27 already covers broad business-suite scope. This backlog records domain depth that may be required if Omnexa is to exceed Odoo/Zoho-class breadth and compete with larger ERP/EPM/CRM/ITSM/business-platform suites without bloating the current active roadmap.

Promotion rule: every candidate requires research, domain ownership, data/financial authority, integration dependencies, security/compliance, localization and business-value analysis before becoming an activated work package.

## 2. Customer growth / marketing

Candidate family: **Marketing Automation & Customer Data Activation**

Potential capabilities:

- campaigns;
- audience/segment activation;
- customer journeys;
- email/SMS/push/messaging orchestration;
- consent/preference linkage;
- attribution;
- lead nurturing/scoring;
- experimentation;
- customer-data activation/CDP-style profiles built from governed sources;
- AI campaign/segment recommendations.

Ownership warning: Customer 360/read profiles must not become a second CRM write model. Consent/privacy authority remains explicit.

## 15. Product Federation principle

Standalone first-party products such as Nexora-like systems are not listed as duplicate Omnexa domains by default. They attach through `XPF-200 Product Federation & App Mesh` using native/embedded/federated/edge modes.

A product becomes a native Omnexa module only when architecture/ownership/lifecycle evidence justifies that choice.

## 16. Promotion criteria

Before any candidate is promoted:

1. research current market/user need;
2. define VOC/CTQs/business outcomes;
3. name authoritative write owner;
4. map overlaps with existing P/X systems;
5. define Business/Data/Process/System Graph contributions;
6. define tenancy/authz/audit/GRC/security;
7. define localization/regulatory boundaries;
8. define APIs/events/workflows/integrations;
9. define performance/reliability/cost;
10. define AI read/draft/execute boundaries;
11. define migrations/upgrade/rollback;
12. define acceptance evidence;
13. route through change control and canonical activation.
