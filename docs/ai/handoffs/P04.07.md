## Prepared P04.07 contract summary

### 1. Payload schema identity is separate from the event envelope

P04.01 remains authoritative for canonical EventID, event type identity and envelope/version semantics.

P04.07 adds an explicit **payload schema version** keyed to stable accepted event identity. It must never overload or reinterpret the P04.01 envelope version.

The logical registry identity is owner + stable event type + explicit payload schema version, with accepted producer/route binding where needed to prevent ambiguous rebinding.

Provider topic names, broker IDs, offsets, delivery tags and caller aliases are not canonical schema identity.

### 2. Accepted historical versions are immutable

One exact event owner/type/version maps to one immutable canonical schema fingerprint.

A contract change receives a new version. Re-registering the same identity with conflicting canonical content fails closed. Rollback/forward recovery must never remap an accepted historical version to different semantics.

### 3. Fingerprints must be deterministic and bounded

The future implementation must freeze:

- supported schema representation/dialect or bounded subset;
- canonicalization rules;
- digest algorithm/encoding;
- size/depth/complexity limits;
- rejection behavior for unsupported constructs.

This preparation deliberately selects no schema technology and no vendor registry.

### 4. Compatibility semantics are explicit

The prepared logical modes are:

- `backward`: candidate/new-schema consumer can accept the declared predecessor payload set;
- `forward`: predecessor consumer can accept candidate/new-schema payloads;
- `full`: both directions pass;
- `exact`: canonical schema fingerprint must be identical.

The exact predecessor comparison set must be declared by later implementation (for example immediate predecessor or bounded retained history) and must not vary silently at runtime.

Same candidate + same predecessor set + same mode must yield the same result. Unsupported or ambiguous schema constructs fail closed.

### 5. Validation is local-only and before protected mutation

The future processing order is:

1. validate/establish P04.01 envelope/event identity;
2. establish accepted P04.02 owner/producer/route binding;
3. resolve exact local accepted schema version;
4. fail closed on unknown/unregistered/unsupported version;
5. validate payload under bounded deterministic limits;
6. only then allow progression toward the protected handler boundary;
7. authorization/business preconditions remain independently authoritative at the actual protected action.

Validation success never grants authorization.

### 6. Remote references and executable schema behavior are forbidden

P04.07 V1 must not fetch remote HTTP(S), registry, DNS or arbitrary filesystem references.

Dynamic code execution, eval, arbitrary plugin execution, shell execution, schema callbacks and schema-derived authorization are forbidden.

If local references are later supported, they must remain immutable/version-bound and bounded by explicit count/depth/size limits.

### 7. Tenant/owner/producer isolation is mandatory

Registry authority belongs to the accepted owner contract, not the tenant or producer payload.

A tenant cannot register, mutate, shadow or select a separate schema fork. The same accepted event type/version has one canonical schema fingerprint across tenants.

Producer/route binding remains P04.02 authority and must be proven before schema-versioned publication/handling is accepted.

### 8. Schema state stays separate from checkpoint/inbox/retry

These facts remain separate:

- P04.03 checkpoint = ordered progress;
- P04.05 inbox = duplicate-safe local protected mutation evidence;
- P04.06 retry/quarantine = failure disposition/attempt/eligibility/terminal evidence;
- P04.07 registry/validation = schema identity/compatibility/payload validation evidence.

Schema validation does not create inbox completion, advance checkpoints, write retry/quarantine state, prove exactly-once processing or establish global ordering.

### 9. Persistence remains an explicit later decision gate

This preparation adds no migration and reserves no migration number.

Accepted `kernel.events` migration 3 is immutable predecessor evidence. Migration 4 is not assumed.

After P04.07 activation, a fresh-main implementation preflight must decide whether registry state is repository-static/generated, PostgreSQL-backed or another local provider-neutral representation. If durable persistence is required, exact owner/version/path/schema budget must be recorded before mutation and separately accepted.
