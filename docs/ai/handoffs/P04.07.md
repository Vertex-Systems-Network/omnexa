## Active P04.07 contract summary

### 1. Payload schema identity remains separate from the event envelope

P04.01 remains authoritative for canonical EventID, event type identity and envelope/version semantics.

P04.07 adds an explicit **payload schema version** keyed to stable accepted event identity. It must never overload or reinterpret the P04.01 envelope version.

The logical registry identity is owner + stable event type + explicit payload schema version, with accepted producer/route binding where needed to prevent ambiguous rebinding. Provider topic names, broker IDs, offsets, delivery tags and caller aliases are not canonical schema identity.

### 2. Accepted historical versions are immutable

One exact event owner/type/version maps to one immutable canonical schema fingerprint. A contract change receives a new version. Re-registering the same identity with conflicting canonical content fails closed. Rollback/forward recovery must never remap accepted historical schema identity.

### 3. Fingerprints must be deterministic and bounded

Before implementation acceptance the later implementation plan must freeze:

- supported schema representation/dialect or bounded subset;
- canonicalization rules;
- digest algorithm/encoding;
- size/depth/complexity limits;
- rejection behavior for unsupported constructs.

No JSON Schema, Avro, Protobuf or vendor registry is selected by activation or this continuity carrier.

### 4. Compatibility semantics are explicit

The accepted logical modes remain:

- `backward`;
- `forward`;
- `full`;
- `exact`.

The exact predecessor comparison set must be frozen by the separately governed implementation plan and must not vary silently at runtime. Same candidate + same predecessor set + same mode must yield the same result. Unsupported or ambiguous constructs fail closed.

### 5. Validation is local-only and before protected mutation

Required ordering remains:

1. establish P04.01 envelope/event identity;
2. establish P04.02 owner/producer/route binding;
3. resolve exact local accepted schema identity/version;
4. fail closed on unknown/unregistered/unsupported schema;
5. validate payload under bounded deterministic limits;
6. only then continue toward the protected handler boundary;
7. evaluate authorization/business preconditions independently at the actual protected action.

Validation success never grants authorization.

### 6. Remote references and executable schema behavior are forbidden

P04.07 V1 must not fetch remote HTTP(S), registry, DNS or arbitrary filesystem references. Dynamic code execution, eval, arbitrary plugins, shell execution, schema callbacks and schema-derived authorization remain forbidden.

### 7. Tenant/owner/producer isolation is mandatory

A tenant cannot register, mutate, shadow or select a separate schema fork. The same accepted event type/version has one canonical schema fingerprint across tenants. Producer/route binding remains P04.02 authority.

### 8. Schema state stays separate from checkpoint/inbox/retry

These facts remain separate:

- P04.03 checkpoint = ordered progress;
- P04.05 inbox = duplicate-safe local protected mutation evidence;
- P04.06 retry/quarantine = failure disposition/attempt/eligibility/terminal evidence;
- P04.07 registry/validation = schema identity/compatibility/payload-validation evidence.

Schema validation does not create inbox completion, advance checkpoints, write retry/quarantine state, prove exactly-once processing or establish global ordering.

### 9. Persistence remains a separate implementation-plan decision

Accepted `kernel.events` migration 3 is immutable predecessor evidence. Migration 4 is not assumed, reserved or authorized.

A later separately governed implementation-plan/worker-plan must decide whether registry state is repository-static/generated, PostgreSQL-backed or another local provider-neutral representation. If durable persistence is actually required, exact owner/version/path/schema/data budget must be recorded after fresh-main migration preflight before any mutation.
