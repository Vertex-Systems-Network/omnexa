## Why P04.06 exists

Accepted durable consumption deliberately permits failures and redelivery. P04.05 prevents the same accepted local protected mutation from being applied twice, but it does not decide:

- whether a failed delivery should be attempted again automatically;
- how many times it may be retried;
- when a later attempt becomes eligible;
- how concurrent retry workers coordinate;
- when failure becomes terminal;
- how a poison event is durably quarantined without permanently blocking ordered progress.

P04.06 defines those policy and persistence boundaries without claiming exactly-once processing, selecting a broker, or granting business-handler authority.

## Failure disposition boundary

Later implementation must classify every authoritative failed delivery into a stable finite disposition:

- `retryable`: a later automatic attempt is allowed by stable structured failure evidence and the accepted operation-safety/idempotency contract;
- `terminal`: automatic retry is forbidden and durable quarantine is required before progress may move past the event;
- `interrupted`: shutdown/cancellation prevented an authoritative result; retry budget is not consumed and checkpoint does not advance;
- `success` / `already_applied`: not failures and must continue through the accepted success/duplicate-safe path.

Classification must use stable machine evidence, never raw error-string matching. P01.03 `Retryable=true` is eligibility evidence only; it never proves an unsafe operation may be repeated. Unknown/unstructured errors fail closed to terminal unless an accepted owner classifier converts them before the P04.06 boundary.

## Bounded retry law

The contract requires finite deterministic retry behavior:

- attempt numbering starts at `1` and includes the first handler attempt;
- every accepted policy has a stable ID/version and finite `max_attempts`;
- retry delay is capped exponential backoff;
- `next_eligible_at` is based on authoritative failure time and normalized UTC;
- no caller-controlled unlimited retry count or zero-delay hot loop is valid;
- exhausted attempt budget becomes terminal and must enter quarantine;
- an in-flight processing identity retains the policy snapshot/version used for its attempt accounting;
- exact numeric bounds are set only during fresh-main implementation preflight and must be finite and operationally bounded.

P01.09's in-memory job retry/schedule primitive is precedent only. It is not a durable event-fabric retry store/timer and must not be silently reused as P04.06 persistence authority.

## Retry state and concurrency

Later implementation must provide durable state logically equivalent to:

- `retry_scheduled`;
- `quarantined`;
- `resolved`.

Required behavior:

1. a retryable authoritative failure records the attempt evidence and next eligibility durably before returning a deferred/scheduled outcome;
2. delivery before eligibility skips the handler, does not increment attempts and does not advance checkpoint;
3. eligible retry first obtains one authoritative claim/lease/CAS;
4. two concurrent workers cannot both own the same next attempt;
5. claim expiry is bounded and does not itself consume retry budget;
6. stale claim completion cannot overwrite a newer attempt, quarantine, or resolved state;
7. persistence/deadlock/serialization failures never create false success/quarantine and must not busy-loop internally;
8. successful completion or P04.05 `already_applied` resolves stale retry scheduling before another automatic handler invocation can occur.

P04.06 concurrency control never replaces P04.05 inbox idempotency.

## Checkpoint / inbox / quarantine separation

Three facts remain separate:

- P04.03 checkpoint = ordered durable progress;
- P04.05 inbox completion = duplicate-safe protected local mutation evidence;
- P04.06 retry/quarantine = failure disposition, attempt budget, eligibility and terminal poison-event evidence.

### Retryable failure

- retry scheduling does not advance checkpoint;
- redelivery before eligibility does not invoke handler;
- redelivery after eligibility may claim the next attempt;
- if the protected mutation previously committed and P04.05 already contains completion while checkpoint advancement failed, redelivery must resolve through `already_applied` and must not become a new retry attempt.

### Terminal / poison event

To prevent one poison event from permanently blocking an ordered scope without erasing its failure:

1. terminal/non-retryable/exhausted state must first commit durable quarantine evidence for the exact processing identity and delivery position;
2. only after authoritative quarantine exists may P04.03 checkpoint progress advance past that exact position;
3. quarantine persistence failure means checkpoint must not advance;
4. crash after quarantine commit but before checkpoint advancement is restart-safe: redelivery sees quarantine, does not run handler again, and may recover checkpoint advancement;
5. checkpoint failure after quarantine must not erase/downgrade quarantine evidence;
6. quarantine is not a P04.05 completion and is not a successful business result.

The later runtime API must make this terminal acknowledgement/recovery path explicit and test the crash gap against real persistence.

## Quarantine data law

Logical dead-letter handling in P04.06 means local durable quarantine evidence, not a broker-specific DLQ.

Bounded safe metadata may include:

- processing identity components;

- safe P01.03 failure code/category/retryability bit;
