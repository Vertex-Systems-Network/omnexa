## Current accepted laws

### Failure disposition and bounded retry

- Stable structured failures are classified deterministically as retryable, terminal or interrupted.
- Unknown/unstructured failure fails closed to terminal unless an accepted owner classifier converts it first.
- Cancellation/interruption consumes no retry attempt and creates no false quarantine.
- Automatic retries are finite, policy-versioned and bounded by accepted maximum attempts/backoff.
- `next_eligible_at` is UTC and based on authoritative failure evidence.

### Durable state and claim authority

- Durable retry state is one of scheduled, quarantined or resolved under the accepted state contract.
- PostgreSQL due discovery uses authoritative database time and a bounded deterministic batch.
- Discovery is not a lease; handler execution requires a successful exact revision `ClaimDue` CAS/lease.
- Claim expiry is bounded; stale claim completion cannot overwrite newer state.
- Attempts/revisions are monotonic and bounded.

### P04.05 inbox / retry composition

Accepted Wave 2D T05 closes the explicit fresh-main gap:

- `InboxApplied` and `InboxAlreadyApplied` are success-like outcomes, never retry failures.
- They may resolve stale retry scheduling only when the retry state already carries an authoritative claim.
- The composition seam has no protected-mutation callback and therefore cannot re-run an already-applied P04.05 mutation.
- Conflict, concurrent, unknown and malformed inbox outcomes fail closed and produce no retry transition.
- Resolution clears eligibility/claim/quarantine state while retaining bounded historical failure evidence.

### Restart persistence

Accepted Wave 2D T06 closes the second explicit fresh-main gap on real PostgreSQL:

- representative scheduled, quarantined and resolved records are committed using one writer pool/store;
- the writer pool is closed completely;
- a fresh reader pool/store is created against the same migrated database;
- exact identity, policy, attempt, revision, failure, eligibility and terminal evidence survives the boundary;
- scheduled state remains awaiting-claim after restart;
- quarantined and resolved states remain non-executable;
- due discovery returns the scheduled state under authoritative time;
- only a fresh successful `ClaimDue` makes scheduled work executable.

## Checkpoint / inbox / quarantine separation

Three facts remain separate and must never be merged semantically:

1. P04.03 checkpoint = ordered durable consumption progress.
2. P04.05 inbox completion = duplicate-safe protected local mutation evidence.
3. P04.06 retry/quarantine = failure disposition, attempt budget, eligibility and terminal poison-event evidence.

Retryable failure does not advance checkpoint. Terminal/exhausted work must commit quarantine before checkpoint advancement. Crash after quarantine commit but before checkpoint advancement is recovered without replaying the handler/terminal mutation. Quarantine is not a successful business result or inbox completion.
