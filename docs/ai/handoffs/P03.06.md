## Objective

Implement only the governed P03.06 Capability Registry contract: a deterministic, versioned, owner-aware metadata registry for module-provided and module-consumed capabilities, without coupling discovery to private implementations or turning registration into invocation authority.

Owner: `kernel.modules`.

## Security and architecture invariants

The following are binding:

- capability registration is metadata/availability only and never grants permission to invoke a capability;
- the owning capability boundary remains responsible for input validation, authorization, tenant/org enforcement and required audit behavior;
- registry lookup cannot bypass `kernel.authorization` or trusted P02 tenant/organization context;
- registry records must not expose private handlers, package-private implementation objects, raw database tables, credentials, secrets or restricted values;
- duplicate/conflicting owner + capability + major-version definitions fail closed;
- disabled, suspended, archived, detached, purged, recovery-ineligible or otherwise unavailable providers cannot be represented as active capability merely because a declaration exists;
- lifecycle state is an availability input, not a permission grant;
- capability metadata cannot create cross-module database write authority;
- public metadata must remain stable/deterministic enough for later evidence, attribution and graph consumers without activating those consumers;
- P03.05 configuration flags/settings cannot be used as a hidden authorization bypass for capability registration or invocation.
