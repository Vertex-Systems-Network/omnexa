## Prepared P04.04 contract boundary

The prepared contract defines only the producer-side transactional outbox reliability primitive required to close the local PostgreSQL state-to-event crash window.

The later implementation, only after separate activation, is expected to preserve these laws:

- canonical event identity/payload remains the accepted P04.01 `events.Envelope`;
- publication ownership remains the accepted P04.02 producer/registration boundary;
- duplicate/restart/no-global-ordering semantics remain compatible with P04.03;
- a required outbox enqueue and the authorized owner mutation participate in the same local PostgreSQL transaction;
- state rollback means the corresponding outbox record does not commit;
- outbox enqueue failure prevents the required owner mutation from committing;
- relay sees only committed pending outbox records;
- publication failure leaves committed work pending/recoverable;
- publish success followed by crash/mark failure may cause duplicate relay after restart;
- a published mark records producer-side publication progress only and does not prove downstream exactly-once mutation;
- no PostgreSQL/broker distributed transaction or end-to-end exactly-once claim is introduced.

## Retained foundations to reuse

P04.04 should compose existing kernel foundations rather than invent parallel infrastructure:

- `kernel/internal/database/transaction.go` provides the retained explicit PostgreSQL transaction boundary;
- the P01 migration runner remains the sole SQL execution/ledger/advisory-lock authority;
- P03.09 migration ownership remains declarative planning/ownership metadata rather than an executor;
- runtime migration files follow `kernel/migrations/<owner>/<version>_<name>.sql` and may mutate only the authoritative owner's objects;
- P01.11 audit transport remains a separate append-only audit concern and is not transactional outbox durability;
- P04.01 envelope validation, payload bounds, tenant/correlation/causation/classification metadata and event identity remain authoritative.

## Runtime design notes for the later activated package

- one owner-bounded transactional enqueue seam that accepts the caller's existing PostgreSQL transaction rather than opening an independent transaction;
- canonical envelope serialization/persistence with stable event identity;
- committed-pending discovery;
- safe relay through the accepted P04.02 publisher abstraction;
- deterministic publication-state advancement that cannot mark success before publish success;
- concurrency control sufficient to avoid state corruption/permanent skip without importing P04.06 scheduling policy;
- focused PostgreSQL integration/crash-window/concurrency tests;
- provider-neutral failure mapping and payload-safe diagnostics;
- one dedicated `verify_p04_04.sh` gate plus an additive governance workflow step.
