## Security and architecture invariants

The following are binding:

- UI visibility never substitutes for backend authorization;
- permission metadata references existing authorization policy and creates no grant;
- `kernel.authorization` remains deny-by-default enforcement authority;
- feature flags remain configuration inputs and cannot grant permission;
- lifecycle/module availability is an availability signal only;
- disabled/unavailable modules cannot present contributions as operational;
- optional-dependency absence degrades only affected contribution paths;
- contribution metadata cannot contain secrets, credentials, raw tenant/org authority or unrestricted executable code;
- contribution metadata cannot expose private handlers/objects/database tables as execution shortcuts;
- trusted tenant/organization context remains governed by P02 contracts;
- no cross-module database write authority, generic RPC/service-mesh authority or hidden invocation mechanism is introduced;
- stable IDs/versions must be deterministic and collision handling must fail safely.
