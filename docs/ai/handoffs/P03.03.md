## Accepted architecture prerequisite — ADR-0012

The P03.03 implementation baseline is:

- schema v1 remains parseable/validated under retained P03.01 semantics;
- manifest parsing uses a bounded top-level schema-version discriminator;
- schema v2 uses a separate strict decoder/validator with exact `{id, constraint}` required/optional module dependency records;
- no parser fallback or schema-v1 string overloading;
- dependency constraint grammar is bounded to 1–16 strict SemVer comparators, maximum 256 bytes, using only `=`, `>`, `>=`, `<`, `<=` and logical AND;
- one strict SemVer 2.0.0 implementation path owns module version/constraint comparison;
- self-dependencies, duplicate IDs and cross-class conflicts fail deterministically;
- P03.02 public registry remains one record per module ID with deterministic duplicate/version-conflict rejection;
- discovery atomically binds each public registry identity to one package-private immutable-by-convention normalized validated manifest snapshot;
- resolver dependency declarations come only from that registry-bound snapshot, not a second independently reparsed raw-manifest set;
- required edges alone drive install/enable topological ordering and release-blocking cycle detection;
- optional absence/incompatibility yields selective degradation and optional edges do not participate in the global required-cycle gate;
- multi-version/SAT solving, automatic dependency selection and external compatibility matrices remain out of scope.

## Objective

Implement only deterministic module dependency validation/resolution as specified by `docs/roadmap/work-packages/P03.03.md`, consuming the retained P03.01 manifest contract, P03.02 deterministic discovery/registry contract and accepted ADR-0012 forward evolution.

## Required boundaries

- owner: `kernel.modules`;
- required dependency presence/version fails closed before install/enable eligibility;
- optional dependency absence/incompatibility produces selective degradation metadata, not global failure;
- platform dependency constraints remain machine-enforced separately;
- deterministic topological order does not depend on discovery enumeration order;
- required cycles and incompatible required constraints are release-blocking invalid states;
- undeclared, forbidden and private cross-module dependency paths are rejected/provable by fixtures;
- resolver output is metadata/eligibility information only and creates no capability, permission, tenant or database authority;
- kernel cannot depend on business modules;
- no direct cross-module private imports or private-schema writes;
- no lifecycle mutations, package installation/download, P04 orchestration, full System Graph runtime, trust/advisory scanning or business behavior;
- no P03.04-P03.11 implementation;
- no AI/model/agent runtime.

## Schema-v1 transition behavior

- v1 manifests with no module dependencies remain resolver-eligible subject to all other gates;
- v1 required dependency strings are not version-resolver eligible and fail closed for install/enable until migrated to schema v2;
- v1 optional dependency strings produce explicit unresolved/degraded optional metadata until migrated;
- no implicit same-major, latest or any-version compatibility inference is allowed.
