## Why P04.05 exists

Accepted P04.03 and P04.04 preserve at-least-once-compatible duplicate behavior:

- a consumer can be redelivered after handling succeeds but checkpoint advancement does not;
- an outbox event can be published more than once after publish succeeds but the producer-side published mark does not persist;
- transport/provider guarantees therefore cannot prove that one protected mutation happened exactly once.

P04.05 provides the local application-idempotency primitive needed to make duplicate delivery safe for one protected consumer scope.

## Processing identity law

Implementation must bind processing to:

- canonical P04.01 EventID;
- stable accepted consumer/handler identity;
- authoritative owner/module scope;
- trusted tenant scope where applicable;
- route/event identity where needed to prevent ambiguous rebinding.

EventID alone is not a global cross-consumer lock. Different legitimate consumers may independently process one event; the same consumer scope must not apply the same protected local mutation twice.

## Atomicity law

For local PostgreSQL protected mutations requiring duplicate safety:

- inbox completion and the protected mutation commit in the same retained P01 local transaction;
- mutation failure rolls back inbox completion;
- inbox persistence failure prevents mutation commit;
- completion is never persisted before the protected mutation commits;
- committed duplicate redelivery returns an explicit already-applied outcome without rerunning the mutation;
- mutation+inbox commit followed by missing P04.03 checkpoint advancement is safe because redelivery resolves as already applied;
- external/non-transactional side effects are not made exactly-once by this primitive.

## Concurrency and conflict law

Two concurrent deliveries of one processing identity cannot both commit the protected mutation. A unique/CAS/locking database invariant may be used, but the contract surface remains provider-neutral and must not introduce P04.06 retry scheduling.

The losing attempt resolves deterministically only after authoritative state is known. Conflicting canonical content reuse, tenant rebinding, owner rebinding or consumer rebinding fails closed. Database failure or cancellation cannot create a false completion marker.

## Checkpoint separation

P04.03 checkpoint state and P04.05 inbox state remain separate facts:

- checkpoint = consumption progress;
- inbox = duplicate-safe local application evidence.

Inbox completion does not automatically advance a checkpoint, and checkpoint advancement does not prove protected mutation exactly-once.
